# ドキュメント駆動開発・フロー

## 1. ドキュメント駆動開発の基本原則

**仕様書が主、コードが副。**

- 実装の根拠は必ず仕様書に存在する
- 仕様書に書かれていないことは実装しない
- コードを書く前に、対応する仕様書を読む

### 仕様書の種類と役割

仕様書はすべて `document/` 配下に格納されている。

```
document/
├── plan/           # 企画書・調査レポート（方針・背景）
├── specification/
│   ├── common/     # 共通仕様（技術スタック・権限表・UIコンポーネント等）
│   ├── page/       # ページ別仕様書（画面・ロジック・導線）
│   └── management/ # 管理画面仕様書
│   └── db/         # データベース仕様
└── data/           # マスタデータ定義（ジャンル・タグ等）
```

実装対象（ページ・URL・機能）とどの仕様書が対応するかは、以下を参照。

> 📄 `document/specification/仕様書トレーサビリティ・マトリクス`  
> 📄 `document/specification/page/ページ一覧仕様書`

### 仕様変更の判断基準

以下のいずれかが変わったとき、仕様変更が発生したと判断する。

| 変更の種類 | 例 |
|-----------|---|
| ユーザーに見える挙動 | ボタンの動作・バリデーションルール・エラーメッセージ |
| 画面構成・表示内容 | 表示項目の追加・削除・並び順の変更 |
| ビジネスロジック | 権限ルール・審査フロー・スコア計算式 |

コードのリファクタリング・パフォーマンス改善・変数名の変更など、実装の内部詳細は仕様書に記載しない。仕様書は要件を伝えるドキュメントであり、実装の細部まで追いかけると可読性が損なわれる。

## 2. 開発フロー

### 通常の実装フロー（仕様書 → コード → テスト）

```
1. 対応する仕様書を読む（上記マッピング表を参照）
      ↓
2. 仕様書に基づいてコードを書く
      ↓
3. 実装に使った仕様書の項目を確認する（→ 第3章）
      ↓
4. 実装完了
```

### 仕様変更が発生したときのフロー

コードを書く中で、ユーザーに見える挙動・画面・ロジックを仕様書と異なる形で実装する必要が生じた場合、**コードと仕様書を同時に更新する**。

```
仕様書と異なる実装が必要になった
      ↓
【必須】対応する仕様書を更新する
      ↓
コードを書く
      ↓
関連する仕様書が他にもないか確認する（下記「影響範囲の確認」参照）
      ↓
必要であれば関連仕様書も更新する
      ↓
実装に使った仕様書の項目を確認する（→ 第3章）
      ↓
更新した関連仕様書の項目も確認する（→ 第3章）
      ↓
実装完了
```

> **NG パターン**: コードだけ変えて仕様書を更新しない。仕様書とコードの乖離は、次の実装者（未来の自分を含む）を混乱させる。

### 影響範囲の確認

一つの変更が複数の仕様書に影響することがある。更新前に以下を確認する。

| 変更した仕様書 | 連鎖して確認すべき仕様書の例 |
|-------------|----------------------|
| ページ仕様書（画面・ロジック） | 共通UIコンポーネント仕様書 / 機能別権限表仕様書 |
| 権限ルール | 機能別権限表仕様書 / 各ページ仕様書 / 管理画面仕様書 |
| 審査フロー | 審査ワークフロー仕様書 / ユーザー管理仕様書 / 通知まわりの仕様書 |
| スコアリングロジック | 信頼度スコアリングシステム仕様書 / レビュー投稿機能仕様書 |
| データ取得バッチ | YouTube定期取得仕様書 / 技術スタック仕様書 |

## 3. テスト原則

### 仕様書の1項目 ＝ 1テスト観点

実装の根拠となった仕様書の記述が、そのままテストケースになる。「仕様書に書いてあること」が実際の動作と一致しているかを確認する。

**例：**
> 仕様書に「未ログイン時はマイリスト追加ボタンを非表示にする」と書かれている  
> → 未ログイン状態でそのボタンが実際に非表示になっていることを確認する

テストの目的は「コードが動くこと」ではなく、**「仕様書に書かれた要件を満たしていること」** の確認である。

### テスト対象の選び方

| 状況 | テストする対象 |
|------|--------------|
| 通常の実装後 | 実装に使った仕様書の該当項目 |
| 仕様変更後 | 変更した仕様書の該当項目 |
| 関連仕様書を更新した後 | 更新した関連仕様書の変更箇所 |

> **NG パターン**: 仕様書を更新したのにテストしない。仕様書とコードの整合性は、確認して初めて保証される。

## 4. E2Eテスト（自動テスト）

第3章のテスト観点は、Playwright の E2E テスト（`e2e/`）として stg に対して自動で確認する。

### 実行の流れ

```
実装・自己確認（tsc / lint / build）
      ↓
stg へデプロイ（クラウド: scripts/deploy-stg-cloud.sh、ローカル: deploy.ps1 stg）
      ↓
E2E を実行（クラウド: npm run test:e2e:stg）
      ↓
結果を完了報告に添える（何件中何件成功、失敗したものと理由）
```

- 接続先は **stg のみ**。本番に対しては実行しない（`e2e/support/env.ts` が本番のホストを拒否する）
- 実行には、クラウド環境の環境変数 `GCP_SA_KEY_STG_B64`（stg 用サービスアカウント。Firestore の読み書きに `roles/datastore.user` が必要）と `STAGING_GATE_PASSWORD`（stg ゲートのパスワード）が要る
- stg はテストモードが常時有効（共通 uiコンポーネント フロント 仕様書 §7.1）。テストはテストモードウィジェットでテスト用会員（一般ユーザー・管理者）としてログインする
- 失敗したテストのスクリーンショットとトレースは `test-results/` に残る

### テストの書き方

| ルール | 内容 |
|------|------|
| 1項目＝1テスト | 実装に使った仕様書の項目をそのままテストにする（第3章）。テスト名・コメントに仕様書と節を書く |
| 追加のタイミング | 新しい機能・仕様変更を実装するたびに、その分のテストを足す。新しいページはスモークテスト（`e2e/smoke.spec.ts`）にも1行足す |
| テストデータ | テストで作るデータの本文は必ず `[E2E]` で始める（`uniqueText()`）。実行の前後に `e2e/support/cleanup.ts` が削除する。新しい種類のデータを作るテストを足したら、cleanup にも削除処理を足す |
| 削除の範囲 | テスト用会員（`users.isTestUser == true`）が作った `[E2E]` データだけを消す。手で作ったデータは消さない |
| ログイン | `userPage`・`adminPage`・`guestPage`（`e2e/support/fixtures.ts`）を使う。同じテストの中で複数の立場を同時に動かせる |
| 画面幅 | desktop（1440px）・mobile（390px）で全テスト、tablet（768px）はスモークのみ |
