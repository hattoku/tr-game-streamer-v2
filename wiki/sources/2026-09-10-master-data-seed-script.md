# マスタデータ投入スクリプトの実装

[[2026-09-09-phase1-plan-review]] で整理した「フェーズ1: マスタデータ投入基盤の整備」を実装した。

## 追加したファイル

- `scripts/lib/firebase-admin.mjs` — Admin SDK初期化（ADC認証、prod/stg切り替え）
- `scripts/lib/tag-id.mjs` — `counters/tags`ドキュメントを使った`TAG-{連番}`のトランザクション発行
- `scripts/data/genres-and-themes.mjs` — ジャンル・テーマの初期データ（ソース文書からの転記）
- `scripts/data/tags.mjs` — ゲームタイトルタグ・再生リストタグの初期データ（同上）
- `scripts/seed-master-data.mjs` — 投入本体。冪等（既存ドキュメントを名前で照合しスキップ）
- `package.json` — `seed:master:stg` / `seed:master:prod` スクリプトを追加
- `firebase-admin`パッケージを依存関係に追加（14.3.0、完全固定。[[依存バージョン固定方針]]踏襲）
- `.gitignore` — サービスアカウント鍵ファイルの誤コミット防止パターンを追加（保険。下記参照）

## 実装時に判明した設計判断

### 1. Admin SDKの認証方式: ADC採用（サービスアカウント鍵ファイルは使わない）

`SECRET_MANAGEMENT.md`は開発フェーズの秘密情報をソースに直書きする方針だが、Admin SDKの
鍵はFirestoreルールを完全にバイパスできる強い権限であり、クライアント向けFirebase設定
（読み取りはセキュリティルールで別途保護される）やYouTube APIキーとは重大性が異なると
判断。過去にv1のFirebase Webアプリキーがハードコードされリークした経緯（HANDOFF.md）も
踏まえ、鍵ファイルを一切生成せず`gcloud auth application-default login`によるADCのみで
運用する方針にした。deploy.sh/ps1が既にgcloud CLIを前提にしているため、追加の学習
コストはない。

### 2. テーマの重複排除（ジャンルとの紐付けなし）

`themes`コレクションに`genreId`フィールドが存在しない（DB設計書3.7節）ことを実装時に
確認。ソース文書（`ゲームジャンル・テーママスタ初期データ.md`）はジャンルごとにテーマを
グルーピングしているが、これは初期データの人間可読性のための整理であり、DB上は
フラットな名前リストとして扱われる。結果として8ジャンル分の「その他」テーマが名前で
衝突するため、投入時に重複排除して1件に統合した。詳細は[[マスタデータ投入方針]]。

### 3. タグの重複排除（ゲームタイトルタグ・再生リストタグ共通コレクション）

`tags`コレクションは用途を区別するフィールドを持たない「共通マスタ」（DB設計書3.8節）
であることを確認。ゲームタイトルタグ・再生リストタグの2つのソース文書に同名タグ
（マルチプレイ・ソロプレイ・長編）が存在したため、名前で重複排除して1件に統合した。

### 4. ソース文書のデータ不整合

`ゲームタイトルタグ初期登録データ一覧.md`の「集計」表は56件（19+37）と記載しているが、
実際に列挙されている項目は54件（19+35）で2件分の差異がある。原因未確認。投入スクリプト
は実際に列挙されている54件のみを転記した。元文書側の確認・修正はユーザー判断待ち。

## 確定した投入件数

ジャンル9・テーマ40・タグ88の合計137件（[[マスタデータ投入方針]]参照）。

## 動作確認の範囲と限界

- `node --check`で全ファイルの構文確認、`npx tsc --noEmit`・`npm run build`で
  ビルドへの悪影響がないことを確認済み。
- **実際のFirestoreへの投入は未実施**。このセッションの実行環境ではgcloud認証操作が
  ブロックされており、ADCの動作確認ができなかった。ユーザー自身が
  `gcloud auth application-default login`実行後、`npm run seed:master:stg`で
  ステージング投入→内容確認→`npm run seed:master:prod`で本番投入、という流れで
  実行する必要がある。
