# フェーズ2.5 ステップ7（ログインと再生リスト登録）実装計画

[[2026-09-11-phase2.5-design-plan]] のステップ6（HANDOFF の番号では7）。フェーズ2.5で最後まで
ノースタイルのまま残っている `/login` と `/playlists/new` に、トークン仕様書 v2.0
（[[2026-09-12-design-direction-crimson]]）の部品を当てる。機能は現状維持が原則で、
仕様書に無いものは足さない（`.agent/rules/development_flow.md`「仕様書が主」）。

## 1. 現状と対象

| ページ | 現状（フェーズ2のまま） | 根拠仕様書 |
|---|---|---|
| `app/(auth)/login/page.tsx` | 素の input 2つ＋「ログイン」「新規登録」ボタン。`?mode=signup` を無視。ラベル・バリデーション・エラー文言なし。Firebase の英語エラーをそのまま表示 | ログイン仕様書 §5（フォーム）・§5.3（エラー）・§8.1〜8.2（作成フォーム・バリデーション）・§12.1〜12.2（レイアウト） |
| `app/(main)/playlists/new/page.tsx` | inline style の管理者専用フォーム。プレビュー・ゲーム選択「モーダル」（実体はインライン div）・完了画面すべて素の要素 | 再生リストを追加する仕様書 §2.1（レイアウト）・§4.1〜4.3（フォーム）・§6.1（完了画面）・§7（エラー） |

`AuthLayout`（ロゴのみのヘッダー、幅 400px）と `Input` / `PasswordInput` / `Field` / `Checkbox` /
`Modal` / `Toast` / `Button` / `Card` / `SectionHeading` はステップ1〜4.5で用意済みだが、
`PasswordInput`・`Field`・`Checkbox` は**まだどのページでも使われていない**。このステップが初使用になるので、
見た目の不備が出たら部品側を直す。

## 2. スコープの線引き

### 2.1 やること

- 2ページの見た目をトークン仕様書 v2.0 に揃える（面・枠・影・入力・ボタン・モーダル・トースト）。
- ログイン仕様書 §5.3・§8.2 のバリデーションとエラー文言（日本語）を入れる。今はフォーム仕様の
  「入力してください」「正しいメールアドレスの形式で」「8文字以上」「一致しません」が無く、Firebase の
  エラーコードが英語のまま出るため、デザイン適用と同時に直す（仕様書に書かれている挙動なので機能追加ではない）。
- `/login?mode=signup`（`SIGNUP_HREF`）で新規登録モードを開く。ヘッダー「アカウント作成」・ボトムタブ
  「マイページ」（未ログイン）・ログイン要求モーダルがすでにこの URL に飛ばしているのに、ページ側が無視している。
- `/playlists/new` のゲーム選択を本物のモーダル（`Modal`）にし、エラーをインライン＋トーストの二段構え（§7.1）にする。

### 2.2 やらないこと（据え置き）

| 項目 | 理由 |
|---|---|
| ソーシャルログイン・パスキー・メール認証（仮登録メール）・初期設定ウィザード（§6〜§8.3〜§10） | フェーズ1で先送り済み（計画書 §3.3）。「──または──」の区切りとソーシャルボタンは**置かない**（押せないボタンを置くより無い方がよい） |
| `/signup` 専用ページ・`/password-reset` ページ | 計画書 §5 のスコープ外。新規登録は `/login` 内のモード切替で代替（計画書 §7 項目2 デフォルト案）。「パスワードをお忘れの方はこちら」リンクは `/password-reset` が無いため**置かない**（§4 判断1） |
| 「ログイン状態を維持する」チェックボックス（§5.2: OFF 24h / ON 7日） | Firebase Auth の永続化は local / session の2択で、時間指定はサーバー側のセッション Cookie が要る。今は永続化を触っていない（既定 = local）。仕様どおりの有効期限は実装できないため**据え置き**（§4 判断2） |
| ログイン成功後の管理者 `/admin` 遷移（§5.4） | 管理画面はフェーズ3以降。全員 TOP（現状どおり） |
| 一般ユーザーの提案フロー・完了画面 §6.2・ゲームタイトル追加提案モーダル §4.2.2・AI説明文生成 §4.1.4・流入元の案内エリア §3 | フェーズ2で管理者専用と決めたスコープ（[[2026-09-10-phase2-plan]]）。API も `requireAdmin`。一般ユーザーは現状どおり「管理者のみ」表示だが、これも部品で組む |

## 3. 実装内容

### 3.1 `/login`（ログイン・アカウント作成）

**構成**（§12.1・§12.2 のメール/パスワード部分。ソーシャル行と「または」は無し）

```
[ロゴ]                                  ← AuthLayout（既存）
ログイン                                 ← SectionHeading（18px bold、中央）
メールアドレス                            ← Field ラベル 12px text-tertiary
[ example@email.com            ]        ← Input type=email
パスワード
[ ••••••••            (目アイコン) ]     ← PasswordInput（表示切替）
[        ログインする        ]           ← Button primary size=full
アカウントをお持ちでない方はこちら          ← 中央のテキストリンク → ?mode=signup
```

新規登録モード（§8.1）: 見出し「アカウントを作成する」、パスワード（確認）を追加、
`Checkbox`「私は13歳以上です」（未チェックで送信ボタン非活性、エラー文言は出さない §8.2）、
ボタン「アカウントを作成する」、下に「すでにアカウントをお持ちの方はこちら」→ `/login`。

**モードの扱い**: `useSearchParams()` の `mode` で決める（`signup` なら作成モード）。
`useSearchParams` を使うコンポーネントは `<Suspense>` で包む必要があるため、ページを
`LoginPage`（Suspense 境界）＋ `LoginForm`（本体）に分ける。モード切替リンクは `<Link>` で
URL を変える（履歴に残る、ヘッダーからの導線と同じ形になる）。切替時に入力とエラーはリセットする。

**バリデーション（送信時、§5.3・§8.2）**

| 条件 | 表示（`Field` の `error`、role=alert） |
|---|---|
| 空欄 | 「入力してください」（各フィールド） |
| メール形式不正 | 「正しいメールアドレスの形式で入力してください」（`<input type=email>` の標準バリデーションは `noValidate` で止め、自前で判定して文言を統一） |
| パスワード 8文字未満（作成時） | 「パスワードは8文字以上で入力してください」 |
| 確認が不一致（作成時） | 「パスワードが一致しません」 |

**Firebase エラーの日本語化**（`FirebaseError.code` で分岐。仕様書に文言があるものはそれに合わせ、
無いものは汎用文）

| code | 表示先 | 文言 |
|---|---|---|
| `auth/invalid-credential` `auth/user-not-found` `auth/wrong-password` `auth/invalid-login-credentials` | フォーム上部のエラー行 | 「メールアドレスまたはパスワードが正しくありません」（§5.3） |
| `auth/email-already-in-use` | メール欄 | 「このメールアドレスはすでに登録されています」（§8.2） |
| `auth/weak-password` | パスワード欄 | 「パスワードは8文字以上で入力してください」 |
| `auth/invalid-email` | メール欄 | 「正しいメールアドレスの形式で入力してください」 |
| `auth/too-many-requests` | 上部 | 「試行回数が多すぎます。しばらく待ってから再試行してください」 |
| その他・ネットワーク | 上部＋トースト error | 「ログインに失敗しました。時間をおいて再試行してください」 |

フォーム上部のエラー行は `text-input-error`（12px）で、`Field` のエラーと同じ見た目。
送信中は `Button loading`（スピナー、§9.3）。`<form onSubmit>` にして Enter で送信できるようにする。

**その他**
- ログイン済みで来た場合は TOP へ（現状どおり）。`loading` 中は `CenteredSpinner`（ページ全体のスケルトンは
  フォーム1枚には過剰）。
- サインアップ成功後の `init-user` 呼び出し→`refreshRole()` は現状の処理を維持。
- `AuthLayout` は既存のまま。フォームは `Card` に**入れない**（§12.1 は背景に直接置く構成。ログイン画面で
  カードを使うと AuthLayout の狭い幅で二重の枠になる）。

### 3.2 `/playlists/new`（再生リストを追加する・管理者）

`app/(main)` 配下なので通常ヘッダー付き。1カラム、`PageContainer` 内で `max-w-[720px]` に絞る
（§2.1 の図はフォームが1枚のカード）。

**アクセス制御**（§1.2）
- `loading`: フォーム形のスケルトン。
- 未ログイン: `/login` へ `router.replace`（現状は文言表示のみ。仕様は「ログインページへリダイレクト」。
  マイリスト・通知と同じ扱いにする）。
- 一般ユーザー: `EmptyState`（「このページは管理者のみ利用できます」＋「TOPへ戻る」）。提案フローは据え置き。

**フォーム**（`Card` 1枚、§2.1）

1. `SectionHeading`「再生リストを追加する」（カードの外）。
2. `Field`「再生リストURL」＋ `Input`（placeholder は §4.1）。`onBlur` でプレビュー取得（現状どおり）。
   URL 形式は送る前に**クライアントで** `list=` の有無を見て、不正なら API を呼ばずインライン
   「YouTubeの再生リストURLを入力してください」＋トースト「URLの形式が正しくありません」（§7.2）。
   `extractPlaylistId` はサーバー用 `lib/youtube.ts` にあり YouTube API キーを含むモジュールなので、
   クライアントには**同じ正規表現だけ**を小さく持つ（`lib/youtube.ts` を import しない）。
3. 注意文「⚠ チャンネルが作成・公開している再生リストのみ登録できます」（`text-md text-text-muted`、
   `AlertIcon`）。
4. 再生リスト確認エリア（§4.1.1）= `CardChildArea`（親フォームの中の子領域。§6.6 の用途どおり）。
   - 取得中: サムネ 16:9 ＋ 2行のスケルトン（§4.1.2）。
   - 取得後: 左サムネ（PC 200px / モバイル全幅、16:9、角丸 8px）＋右にタイトル（15px medium・2行省略）、
     チャンネルアイコン（24px 円形）＋名前、「動画数: N本」（`CountLabel` は「N話」用なので使わない。
     この画面の文言は仕様書どおり「動画数: N本」）。
   - チェック結果の行: ✅／❌ を絵文字ではなく `CheckIcon`（`text-toast-success`）／`AlertIcon`
     （`text-input-error`）で描く。順序と省略ルールは §4.1.1（非公開なら一致チェックの行は出さない）。
   - チャンネル状態（§4.1.3）: 両チェック OK のときだけ。未登録なら `Field`「チャンネルの説明文（任意）」
     ＋ `Textarea`（AI 生成は据え置きなので手入力のみ。ラベルに「任意・手入力」と明記）。
   - 取得失敗: エリアを出さず、URL の `Field` にインラインエラー（§7.2 の文言）＋トースト。
5. `Field`「ゲームタイトル」＋選択ボタン（§4.2）。
   - 未選択: `Button secondary` 幅100%「ゲームタイトルを選択する」＋右端 `ChevronDownIcon`。
   - 選択済み: 同じボタンにタイトル名を表示し、横に `Button ghost` の `XIcon`（解除）。
   - 送信を押せない理由がゲーム未選択のときのインライン「ゲームタイトルを選択してください」は、
     ボタンが非活性なので通常出ない（§7.2 の注記どおり実装は保険のみ）。
6. 送信ボタン `Button primary`「登録する」（右寄せ、非活性条件は §4.3 と現状の `canSubmit` を維持）。
   送信中は `loading`。API エラーは §7.2 の表に従いインライン（URL 欄 or ボタン上）＋トースト。

**ゲームタイトル選択モーダル**（§4.2.1）= `Modal`（`maxWidthClassName="max-w-[560px]"`）
- 上部に `Input`「ゲームタイトルを検索...」＋ `SearchIcon`、入力ごとに絞り込み（現状の `includes`、
  大文字小文字と全角半角は据え置き）。開いたらフォーカスを検索欄に（Radix の `onOpenAutoFocus`）。
- 一覧はモーダル内スクロール（`max-h-[50dvh] overflow-y-auto`）。行 = `packageImageUrl` の縦長サムネ
  （40×56px、無ければグレーのプレースホルダー）＋タイトル。行はボタンで、ホバー `bg-bg-hover`（§13.3 の項目と同じ）。
- 候補 0 件: 「該当するゲームタイトルがありません」。
- フッターの「ゲームタイトルの登録を提案する」リンクは一般ユーザー向け（§4.2.2 対象外の注記で管理者には出さない）
  なので、管理者専用の今は**出さない**。
- `games` の読み込みは現状どおり `getDocs(collection(db,'games'))`（ゲストR可のコレクション）。

**完了画面**（§6.1、同一ページ内で切替）
- 見出し「登録が完了しました」（`CheckIcon` を `text-toast-success` で先頭に。絵文字は使わない）。
- `Card`: サムネ 16:9 ＋タイトル・チャンネル（アイコン＋名前）・「🎮 ゲームタイトル名」相当は
  `Tag` でゲーム名（`PlaylistGrid` のゲーム名タグと同じ見せ方）・「動画数: N本」。
- ボタン: `LinkButton primary`「再生リストを見る」→ `/playlists/{id}`、`Button secondary`「続けて登録する」
  → `resetForm()`（ゲーム一覧は再取得しない）。
- 登録成功時にトースト success「再生リストを登録しました」も出す（UI 仕様書 §6.4 の用途に沿う）。

### 3.3 共通部品への手入れ（必要になったら）

| 部品 | 想定される手入れ |
|---|---|
| `Field` | 関数 children で `aria-invalid` を渡す形を `Input` / `PasswordInput` で初めて使う。`PasswordInput` が `aria-*` を素通しできるか確認 |
| `PasswordInput` | 目アイコンの当たり判定（今は `p-1`）。モバイルで 32px 以上になるよう `p-2` に広げる可能性 |
| `Checkbox` | `accent-color` の見え方を初確認 |
| `Modal` | 中身が長いときの内側スクロール（今は Content 全体が `overflow-y-auto`）。検索欄を固定し一覧だけスクロールさせたいので、`Modal` の `children` 側で組む（Modal 自体は変えない） |
| `icons.tsx` | 必要なら `GamepadIcon`（🎮 の代替）。無ければ `Tag` で済ませる |

仕様書に無い値を足すことになったら、先に仕様書へ追記する（[[デザイントークン運用方針]]）。

## 4. ユーザーに確認した判断（2026-09-12 デフォルト案どおりで決定）

1. **「パスワードをお忘れの方はこちら」リンク** — **置かない**。`/password-reset` が無く404に落ちるため。
   Firebase の `sendPasswordResetEmail` で最小実装は可能だが、§9 の画面（送信済み画面・登録有無を
   明かさない挙動）まで含めると別ステップの量になる。**後日実装の課題として HANDOFF 未解決事項 8 に記録**。
2. **「ログイン状態を維持する」チェックボックス** — **置かない**。§5.2 の 24h/7日は Firebase クライアント
   SDK だけでは実現できない（永続化は local / session の2択）。置くなら見た目だけの切替になり仕様と
   挙動がずれる。**後日実装の課題として HANDOFF 未解決事項 9 に記録**（サーバー側セッション Cookie 方式が要る）。
3. **一般ユーザーが `/playlists/new` を開いたときの表示** — 「管理者のみ」の `EmptyState`。提案フローはフェーズ3。
4. **ログイン成功後の遷移** — 全員 TOP（現状どおり）。`?next=` で元のページへ戻す仕組みは仕様書に無いので足さない。

## 5. 作業順とコミット

1ステップ1コミットの慣例どおり `feat: フェーズ2.5ステップ7を実装（ログイン・再生リスト登録のデザイン適用）` の1コミット
（Wiki の記録は別コミット）。順序:

1. `/login`（小さい方から。`Field` / `PasswordInput` / `Checkbox` の初使用で部品の不備を先に潰す）
2. `/playlists/new` フォーム → ゲーム選択モーダル → 完了画面
3. `npx tsc --noEmit` / `npm run build`
4. 実ブラウザ確認（§6）
5. 各ページ冒頭コメントの「フェーズ2.5ステップ6で行う」等の記述を更新、HANDOFF.md の 7 を完了に、
   Wiki（この計画の結果を `2026-09-12-login-and-register-design.md` として記録、index / log 更新）

## 6. 動作確認（`scripts/dev/screenshot.mjs`、ユーザーの `npm run dev` 前提）

| 確認 | 手順 |
|---|---|
| ログイン初期・作成モード（1440 / 390） | `/login`、`/login?mode=signup` を撮影 |
| バリデーション表示 | `{"click":"ログインする"}` を空欄で押して各欄の「入力してください」を撮影 |
| 認証エラー文言 | 存在しないメールで送信 → 「メールアドレスまたはパスワードが正しくありません」 |
| 新規登録の成功 | **本番 Firebase Auth にユーザーが増える**ので撮影スクリプトでは行わない。ユーザー側でテスト用メールで1回、または省略 |
| 登録フォーム（管理者） | TOP で「管理者でログイン」→ `/playlists/new`。URL 未入力・不正 URL・取得中・取得後（登録済みの再生リストを入れて「すでに登録されています」表示）を撮影 |
| ゲーム選択モーダル | 「ゲームタイトルを選択する」click → 撮影 → 検索語を `eval` で入れて絞り込み |
| 完了画面 | **本番 Firestore に再生リストが増える**（ステップ3の注意と同じ）。新規登録は行わず、完了画面は `completion` state を `eval` で注入できないため、コード上で確認 or ユーザーが実登録するときに目視 |
| 一般ユーザー・未ログイン | 「一般ユーザーでログイン」→ `/playlists/new`（管理者のみ表示）、ログアウト → `/playlists/new`（`/login` へ） |

## 7. 見積もり

計画書の目安どおり 1 セッション。`/login` 0.3、`/playlists/new` 0.5、確認と記録 0.2。
