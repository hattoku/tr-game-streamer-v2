# ゲーム未設定の再生リスト — ユーザーがゲームを登録する（段階C）と新しいゲームタイトルの提案

PR #20（`5d9a66a`、2026-11-01）と PR #21（`eda9cee`、2026-11-04）。仕様は 再生リスト詳細 v1.15・v1.16、収集候補レビューUI v3.2、審査ワークフロー v12.1 §14.3.1、データモデル v2.3・v2.4。

## PR #20: 既存のゲームを選んで登録（審査なし）

- 再生リスト詳細に「ゲームが未設定です」のカードと「ゲームを登録」（`GameRegisterCard`）。未ログインはログインの案内だけ
- `POST /api/playlists/[playlistId]/game`: `gameId` が null のときだけ（先に付いていれば 409）。1人1日（日本時間の暦日）20件まで（429）。
  カウンター `game_link_counters` を**ゲームを付けるのと同じトランザクションで**数えて競合を防ぐ
- 管理者が外したゲーム（`rejectedGameIds`）は選べない（409）。履歴は `playlist_game_changes`
- 管理「ゲーム未設定」に「ユーザーが登録したゲーム」と「戻す」
- 名称は「ゲームを教える」ではなく「ゲームを登録」（ユーザー指定）

## PR #21: 新しいゲームタイトルを提案（審査あり）

- ユーザー指摘: 既存のゲームから選べるケースは稀（再生リストは審査を通ったものだけ出る）。既存に無い場合の導線が要る
- 「新しいゲームタイトルとして入力する」→ 名前と備考で提案。入力中に似た名前の登録済みゲームを出す
- `POST /api/playlists/[playlistId]/game-proposal`: ゲーム未設定だけ・同名があれば 409・同じ再生リストに審査中の提案があれば 409・直近24時間に5件まで（429）
- 審査は既存の `workflows`（`game_title_register`）を `proposalData.playlistId` 付きで再利用。運営は「登録して承認」か「既存のゲームに付けて承認」。承認時に別のゲームが付いていたら 409
- 残リスク（低頻度で見送り）: 同時送信で提案が重複しうる、2人の管理者の同時承認が競合しうる。提案まわりは作り直す予定なので、いったんこのままマージ（ユーザー判断）
