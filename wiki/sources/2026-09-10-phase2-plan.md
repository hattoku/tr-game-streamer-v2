# フェーズ2計画の精緻化

HANDOFF.mdのフェーズ2「YouTube埋め込みプレーヤー」「マイリスト機能」「新着通知」は
並列3項目に見えるが、関連仕様書を調査した結果、実質一直線の依存チェーンであることが
判明した。調査結果をもとに実装順序を確定した。

## 依存チェーン

```
gamesテストデータ ─┐
                   ├→ YouTube Data API連携基盤 → 再生リスト登録フロー（管理者用）
                   ┘         ↓                          ↓
                    playlists/videos/channelsに実データ投入
                          ↓                    ↓
                    マイリスト機能          動画プレーヤー（連続再生・視聴進捗）
                          ↓
                      新着通知
```

## YouTube連携の2つの仕組み（混同注意）

1. **登録フロー**（`ページ 再生リストを追加する 仕様書.md`v3.6、`/playlists/new`）:
   管理者がYouTube再生リストURLを貼り付け→YouTube Data APIで直接fetch→
   既存の`games`から検索選択（その場で新規作成する導線はない）→
   新規チャンネルは自動作成（AI説明文生成含む、今回は手入力に簡略化）→
   `playlists`/`videos`/`channels`へ全件書き込み。
2. **定期取得バッチ**（`共通 youtube定期取得仕様書.md`v1.6）:
   既存の`playlists`のみを対象に、RSS（無料枠）→失敗時API、で新着動画を検知・
   更新する。Cloud Functions（2nd gen）+ Cloud Schedulerが前提で、
   本リポジトリには`functions/`ディレクトリすら存在しない。**今回は本格導入せず、
   同じロジックを管理画面の手動再取得ボタン（Next.js API Route）として実装し、
   新着通知の発火ロジック自体は検証できるようにする**（ユーザー確認済み）。

## Firestoreスキーマギャップ（3件、DB設計書に未記載）

- `mylist`（DB設計書3.11節）: 現状`userId, playlistId, createdAt, updatedAt`の4項目のみ。
  `ページ マイリスト機能仕様書.md`が要求する視聴ステータス（見たい/視聴中等）・
  再生リスト単位の逆順トグルのフィールドがない。
- `users`（DB設計書3.1節）: 連続再生ON/OFFのグローバル設定、プッシュ通知の
  種別ごとON/OFF設定（`notificationSettings`的なもの）が現行スキーマにない。
- `notifications`: ユーザー向け通知コレクションがDB設計書の29コレクション一覧に
  存在しない。`admin_notifications`（3.19節）は管理者向けの別物で流用不可。

いずれも実装前にスキーマを設計し、`Firestore データモデル設計書.md`へ追記してから
着手する（`.agent/rules/development_flow.md`のドキュメント駆動開発方針）。

## 確定した実装順序

1. テスト用`games`データ投入（マスタ投入と同じ要領のスクリプト）
2. YouTube Data API連携基盤（`lib/youtube.ts`等）
3. 再生リスト登録フロー（管理者専用の最小版、AI説明文生成は手入力に簡略化）
4. マイリスト機能（`mylist`スキーマ拡張含む）
5. 動画プレーヤー（`users`スキーマ拡張含む。4とは並行可）
6. 新着通知（`notifications`スキーマ新規設計、手動トリガー経由）
