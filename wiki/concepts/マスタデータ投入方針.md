# マスタデータ投入方針

フェーズ1「マスタデータ投入」の実態整理。[[2026-09-09-phase1-plan-review]] での検討結果を
[[2026-09-10-master-data-seed-script]] で実装に落とし込んだ。

## 投入対象と規模（実装時に確定した正確な件数）

`document/master/`配下の初期データが対象。重複排除後の確定件数は**ジャンル9・
テーマ40・タグ88の合計137件**（前回セッション時点の「約170件」という概算より
精緻化された）。

| 種別 | 件数 | ソース |
|---|---|---|
| ゲームジャンル | 9 | ゲームジャンル・テーママスタ初期データ.md |
| ゲームテーマ | 40（ソース上は47件、うち「その他」が8ジャンル分重複するため重複排除後40件） | 同上 |
| タグ（ゲームタイトル・再生リスト共通） | 88（ゲームタイトルタグ54件＋再生リストタグ37件のうち、マルチプレイ・ソロプレイ・長編の3件が両ソースに重複するため重複排除後88件） | ゲームタイトルタグ初期登録データ一覧.md / 再生リストタグ初期登録データ一覧.md |

**`games`（実ゲームタイトル）は対象外**: 楽天ブックスAPI取得＋将来のAI運営者新作検知
バッチで賄う設計（`Firestore データモデル設計書.md`3.5節）のため、フェーズ1の手動投入
には含まれない。

### 判明した設計・データ上の注意点

- `themes`コレクションに`genreId`フィールドは存在しない（DB設計書3.7節・管理画面仕様書
  7.3節ともに記載なし）。ソース文書のジャンル別グルーピングは投入データ作成時の便宜であり、
  実際のテーママスタはフラットな名前リストとして扱われる。これによりジャンル横断で同名の
  「その他」テーマが重複するため、投入時に名前で重複排除して1件に統合する。
- `tags`コレクションは「ゲームタイトル・再生リスト共通」（DB設計書3.8節）で、用途を区別する
  フィールドがない。ゲームタイトルタグと再生リストタグの2つのソースに同名タグ
  （マルチプレイ・ソロプレイ・長編）が存在するため、こちらも名前で重複排除して1件に統合する。
- `ゲームタイトルタグ初期登録データ一覧.md`の「集計」表は56件（19+37）と記載しているが、
  実際に列挙されている項目は54件（19+35）で2件分の差異がある。元文書側の集計ミスの
  可能性があり未確認。投入スクリプトは実際に列挙されている54件のみを転記している
  （`scripts/data/tags.mjs`参照）。

## 投入方法上の制約と実装

- `firestore.rules`で`genres`/`tags`等マスタ系コレクションは`write: if isAdmin()`のみ
  許可（[[firestoreセキュリティルール方針]]参照）。認証実装前の現段階では、クライアント
  SDKでは書き込めず**Admin SDK（ルールをバイパス）での投入が必須**。
  `scripts/lib/firebase-admin.mjs`で実装。
- 認証情報は**サービスアカウント鍵ファイルを使わず、Application Default Credentials
  （`gcloud auth application-default login`）を使う方針にした**。`SECRET_MANAGEMENT.md`は
  「開発フェーズの秘密情報はソースに直書き」という方針だが、Admin SDKの鍵は
  Firestoreルールを完全にバイパスできる強い権限であり、クライアント向けFirebase設定や
  YouTube APIキーとは重大性が異なる。過去にv1のFirebase Webアプリキーがハードコードされ
  リークした経緯（HANDOFF.md）もあるため、この鍵種別は同方針の対象外として、鍵ファイルを
  一切生成しない運用にした。`.gitignore`にもサービスアカウント鍵ファイル名パターンを
  念のため追加済み。
- `tags`コレクションのIDはFirestore自動IDではなく`TAG-{連番}`（1始まり、ゼロ埋めなし）
  という独自ルール（`管理 マスタ管理仕様書.md`6.2/6.3節）。ゲームタイトルタグ・再生
  リストタグは同一`tags`コレクションを共有するため採番も共通。`scripts/lib/tag-id.mjs`が
  `counters/tags`ドキュメントをトランザクションで更新して連番を発行する。
  **将来、管理画面からのタグ追加・ユーザーによるタグ付与機能を実装する際も、必ずこの
  `counters/tags`ドキュメント・トランザクション手順を再利用すること**。独自に連番を
  計算する実装を別途作ると採番が衝突する。
- ジャンル・テーマにはID採番規約の記載がないため、Firestore自動IDを使用。
- 投入スクリプト（`scripts/seed-master-data.mjs`）は冪等: 既存ドキュメントを名前で照合し
  スキップするため、何度実行しても重複作成されない。`npm run seed:master:stg` /
  `npm run seed:master:prod`で実行。

## タグのカテゴリ情報について（Firestoreには保存しない）

`ゲームタイトルタグ初期登録データ一覧.md`・`再生リストタグ初期登録データ一覧.md`は
タグを「遊び方系」「IP系」「実況スタイル系」等のカテゴリに分けて記載しているが、
`tags`コレクションにも管理画面のタグ追加フォームにもカテゴリを保持するフィールドは
存在しない。一方、`document/specification/page/ページ ゲームタイトル 探す 仕様書.md`・
`document/specification/page/ページ 再生リストを探す 仕様書.md`（いずれも4.4節）は、
タグ絞り込みUIの表示件数制御に「初期登録データ一覧.mdの構成に準ずる」カテゴリ分けを
使うと明記している。

→ **カテゴリはFirestoreのデータではなく、探すページ実装時にフロントエンド側で使う
静的な表示グルーピング情報**と判断した（運用開始後に管理画面から追加される運営者
タグはカテゴリの対象外という設計）。`scripts/data/tags.mjs`はソース文書のカテゴリ構造
（ゲームタイトルタグ: 遊び方系19件/IP系35件、再生リストタグ: 実況スタイル系12件/
プレイスタイル系21件/編集スタイル系4件）を保持したまま定義し、Firestore投入用の
フラット配列はそこから導出している。探すページ実装時はこのファイルの
`GAME_TITLE_TAG_CATEGORIES` / `PLAYLIST_TAG_CATEGORIES` を参照すればソース文書を
読み直す必要がない。

  フェーズ1「マスタデータ投入実行」はこれで完了。
