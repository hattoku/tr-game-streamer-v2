# ステージング環境運用方針

本番（`tr-game-streamer`）とステージング（`tr-game-streamer-stg`）の構築タイミングに
関する方針。[[2026-09-09-phase1-plan-review]] での検討結果。

## 基本方針: 「設定は都度同期、データと検証は後回し」

- **今すぐ本番と同時にやる**（コストが低く、後回しにすると乖離が蓄積して大工事になるため）
  - Firestoreルール・インデックスのデプロイ
    （2026-09-20以降は`deploy.sh`/`deploy.ps1`の手順2（Cloud Runデプロイの前）に
    `firebase deploy --only firestore:rules,firestore:indexes`が組み込まれており、通常デプロイで
    自動的に反映される。それ以前は`hosting`のみが対象で、ルール変更時に手動で両環境に打つ運用
    だった。ルールだけ先に反映したい場合は従来どおり手動で
    `firebase deploy --only firestore:rules,firestore:indexes --project <project-id>`）
  - Firebase Authenticationのプロバイダ有効化（メール/パスワード・Google）
- **フェーズ4（検証・本番デプロイ）まで後回しでよい**
  - マスタデータの実投入（[[マスタデータ投入方針]]参照）
  - 実ユーザーでのE2E動作確認

## 背景

- 個人開発でまだ本番にも実ユーザーがいない段階のため、フェーズ1〜3でスキーマ・ルールが
  頻繁に変わるたびにステージングのデータも作り直すのは非効率。
- 一方、設定（ルール・インデックス・Authプロバイダ）は反映漏れに気づきにくく、フェーズ4で
  一気に反映しようとすると差分洗い出しの手間が大きくなる。

## 現状（2026-09-20時点）

フェーズ4.5ステップ7の棚卸し（[[2026-09-20-phase4.5-step7-partial]]）で、Firebase Rules API・
Identity Toolkit Admin APIを直接叩いて読み取り専用で確認。「設定は都度同期」の方針どおり、
ルール・Authプロバイダはprod/stgで一致していた。

- Firestoreルール: prod・stg・リポジトリの`firestore.rules`が完全一致。
- Firestoreインデックス: ほぼ一致だが、prodにのみ`reviews`の未使用と思われる古いインデックス
  （`createdAt`基準。現行スキーマは`postedAt`）が1件残っている。stgには無い＝リポジトリの
  `firestore.indexes.json`が正。
- Authenticationプロバイダ（メール/パスワード・Google）: prod/stg一致。
  2026-09-09時点で「stg未確認」としていたが、いつの間にか（おそらくフェーズ4のstg構築時に）
  解消されていた。
- マスタデータ（genres/themes/tags）: 基本一致。tagsのみprodが3件多いが、いずれも
  フェーズ4.5以降の実運用・E2E残置によるもので方針からの逸脱ではない。
- 実データ（playlists/reviews/mylist等）: 方針どおりprodにのみ蓄積されており、stgは
  最小限のテストフィクスチャのみ。

## ローカル開発の接続先（2026-09-20追加）

**`NEXT_PUBLIC_APP_ENV=prod`と明示したときだけ本番、それ以外はすべてstg**（`lib/app-env.ts`）。
以前は逆（stgと明示しない限り本番）だったため`npm run dev`が本番Firestoreに向いており、
フェーズ1〜4.5のE2Eはすべて本番に対して行ってテストデータを都度掃除していた。
[[2026-09-20-env-default-stg]]で反転。

- 日常の実装・E2E確認: `npm run dev`（stg）
- 本番接続が必要なときだけ: `npm run dev:prod`
- テストモード（`NEXT_PUBLIC_TEST_MODE`）は本番では無効（`TEST_MODE_ENABLED = !IS_PROD && ...`）
- Cloud Runデプロイは`deploy.ps1 [stg|prod]`→`cloudbuild.yaml`の`_APP_ENV`で明示するので影響なし
- Firebase Webアプリ設定（apiKey等）は`lib/firebase.ts`直書きのみで、環境変数による上書きは廃止
  （`.env.local`に旧Webアプリ登録のappIdが残っていた等、設定源の二重化でドリフトしていたため）

## 環境間で共有されたままのもの（備忘録）

シークレット（`YOUTUBE_API_KEY`・`CRON_SECRET`・Basic認証）はstg/本番で同一値。
`YOUTUBE_API_KEY`はYouTube Data APIのクォータを両環境で共有する。当面は対応不要と判断、
分離案はHANDOFF.md未解決事項13に記載。本番→stgのデータコピー手段（`gcloud firestore export/import`）
は後日の課題（`npm run dev`がstgを向くようになり、stgがほぼ空なのが実装作業に効いてくるため、
フェーズ5で本番データが溜まってきた頃か、実装中にstgのデータ不足で困った時点でやる）。
