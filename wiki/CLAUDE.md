## 役割分担: もう一つのWiki（ak_tr_game_streamer_dev）との違い

このプロジェクトには、目的の異なる2つのWikiが存在する。

- **このWiki（`tr-game-streamer-v2/wiki/`）— コーディング支援用**
  実装レベルの変更履歴・技術的決定・デバッグメモ・「このコードはなぜこう
  書かれているか」など、**コードに近い情報**を記録する。日々の実装作業を
  支援するための、コードベースに紐づいたWiki。
- **`c:\development\ai_knowledge\ak_tr_game_streamer_dev`（別リポジトリ）
  — 設計を含む開発全般の検討用**
  企画・仕様・アーキテクチャ設計・インフラ構成・意思決定の経緯など、
  **プロダクト開発全体の文脈**を扱う。`document/`配下の企画書・仕様書の
  要約もこちらに蓄積される。

判断に迷う場合の目安: 実装の詳細・変更理由の記録に近ければこちら。
設計判断・企画・仕様そのものの検討ならak_tr_game_streamer_devへ。
両方に関係する話題は、それぞれの観点から別々に記録してよい（重複を恐れない）。

## 3層構造

1. **Raw Sources（素材層・不変）**
   `git log` / コミット差分、実装セッションのやり取り、デバッグ時に判明した
   事実など、**コードに直結する一次情報源**が中心。`document/`配下の企画書・
   仕様書そのものの要約は ak_tr_game_streamer_dev の役割のため、このWikiでは
   実装判断の根拠として参照する程度に留める（コピーしない）。
   Claudeはraw情報源を読み取り専用として扱い、直接編集しない。

2. **Wiki（このディレクトリ・Claude管理）**
   `index.md` / `log.md` / `overview.md` / `sources/` / `entities/` /
   `concepts/` / `analyses/` からなる。Claudeが作成・更新・相互リンクの
   維持を行う。ユーザーは基本閲覧のみ。

3. **Schema（このファイル・ユーザーとClaudeで共進化）**
   このCLAUDE.mdがワークフロー・命名規則を定義する。運用しながら
   実態に合わせて更新していく。

## ディレクトリ構成

```
wiki/
├── CLAUDE.md       このファイル（ワークフロー定義）
├── index.md        コンテンツ索引（カテゴリ別ページ一覧）
├── log.md          追記専用の操作ログ
├── overview.md     プロジェクト全体像のサマリー
├── conventions.md  ページ形式・命名規則
├── sources/        実装セッション・重要な変更のサマリーページ（1変更/1セッション=1ページ）
├── entities/       コードベース内の主要なモジュール・外部連携のページ
│                   （例: lib/firebase.ts、middleware.ts、YouTube Data API連携）
├── concepts/       実装上のパターン・技術的決定・ハマりどころのページ
│                   （例: 環境変数/シークレット管理方針、デプロイフロー）
└── analyses/       複数の変更・調査を横断した比較・考察ページ
```

## ワークフロー

### Ingest（取り込み）
実装作業が一段落したとき、重要な技術的決定・変更をしたとき、または
ユーザーから「これをwikiに記録して」と依頼されたとき:
1. 何が変わった・決まったかをユーザーと確認する
2. `sources/<slug>.md` にサマリーページを作成／更新する
   （frontmatterに `date` / `updated`、関連コミットがあれば記録する）
3. 関連する `entities/` `concepts/` ページを新規作成または更新し、
   `[[page-name]]` 形式で相互リンクする
4. `index.md` を更新する
5. `log.md` に `## [YYYY-MM-DD] ingest | <対象ドキュメント名>` 形式で追記する

### Query（質問応答）
ユーザーからの質問に対し:
1. `index.md` を読み、関連ページを特定する
2. 該当する `sources/` `entities/` `concepts/` ページを読み合成して回答する
3. 有用な回答は新しい `analyses/` ページとして保存してよいかユーザーに確認する

### Lint（健全性チェック）
定期的に、またはユーザーの依頼で以下を確認し、必要なら修正する:
- ページ間の矛盾がないか
- `document/` の更新で古くなった記述がないか
- 被参照のない孤立ページがないか
- 記述はあるがページ化されていない重要conceptがないか
- 相互リンクの欠落がないか
