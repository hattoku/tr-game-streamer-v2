## 1. 概要

リブランディング段階7（精査 §6.4）。これまで検索面の一覧（再生リストを探す・チャンネル・ゲームタイトル・TOP・ゲーム/チャンネル詳細）は、公開かつ掲載中の再生リストを**全件ブラウザに読み込んで**から絞り込み・並べ替え・ページングしていた。掲載チャンネルを80件ほど取り込むと再生リストは約5,300件になり、1回の表示ごとに5,300件分の Firestore 読み取りとデータ転送が発生して重くなる。

そこで、絞り込み・並べ替え・ページングを**サーバー側**で行い、画面には**1ページ分（20件）だけ**を返す形に作り直す。

| | これまで | これから |
|---|---|---|
| 画面が受け取る件数 | 掲載中の全件（約5,300件を想定） | 1ページ分（20件）。TOP は各カルーセル最大20件 |
| Firestore の読み取り | 表示のたびに全件 | サーバーが最初に1回全件を読み、その後は変わった文書の分だけ（§2.2） |
| キーワード検索 | ブラウザ内で部分一致 | サーバー側で部分一致（全角半角・カタカナひらがなの違いも無視、§4.1） |
| ページ送り | ブラウザ内 | サーバー側（範囲外のページは最後のページに丸める） |

検索面に出すのは、これまでどおり**公開（`isPublic == true`）かつ掲載中（`listingStatus == 'listed'`）**の再生リストだけ（コンテンツ収集機能仕様書 §10.7）。マイリスト・視聴履歴・再生リスト詳細は対象外（今のまま）。

## 2. 仕組み

### 2.1 なぜ Firestore のクエリで直接引かないか

Firestore には次の機能が無く、今の画面の検索条件を満たせない。

- 部分一致（「ドラクエ」を含む、など）の検索
- 複数のタグを**すべて含む**（AND）の絞り込み（`array-contains` は1つしか使えない）
- 絞り込んだ結果に対するゲーム・チャンネルごとの集計（再生リスト数・動画数・ピックアップ）

外部の検索サービス（Algolia など）を入れるほどの規模ではないため、**サーバー（Cloud Run のインスタンス）のメモリに検索用の索引を持つ**。5,300件程度なら索引は数十MB・検索は数ミリ秒で、今の Cloud Run（512MiB）で足りる。数万件を超えるようなら外部の検索サービスを検討する。

### 2.2 索引を最新に保つ方法

| 項目 | 方針 |
|---|---|
| 索引に持つもの | 公開かつ掲載中の `playlists`、`channels`・`games`・`tags` の全件（カード・絞り込み・集計に要る項目だけ） |
| 最新に保つ方法 | Firestore の変更の購読（Admin SDK の `onSnapshot`）。最初の1回だけ対象を全件読み、その後は**変わった文書の分しか読まない**（読み取りの課金も変わった分だけ） |
| 反映の速さ | 画面からの書き込み・管理画面・定期処理・別のインスタンスからの書き込みも、数秒以内に一覧へ反映される |
| しばらく使われなかったとき | 30分以上使われなかったインスタンスは、CPU が止まっている間に購読が切れて遅れている可能性があるため、次に使うときに購読を張り直して全件を読み直す（Firestore も30分以上切れた購読の再開は全件の読み取りとして課金するため、張り直しても読み取りは増えない） |
| 起動直後 | 最初の呼び出しで全件を読み込む（stg の86件で約2秒）。25秒以内に終わらなければ 503 を返す |
| インスタンスが複数のとき | インスタンスごとに索引を持つ（それぞれが購読する） |
| 実装 | `lib/catalog-server.ts`（サーバー専用）。API は `app/api/catalog/*` |

> **読み取り量の目安**: 1日の読み取りは「インスタンスが起動した（または30分以上空いた後に使われた）回数 × 約5,300件」＋「変わった再生リストの数」。これまでの「表示の回数 × 約5,300件」に比べ、表示が増えても読み取りはほとんど増えない。

## 3. API

いずれも `GET`、ログイン不要（検索面は未ログインでも見られる）。応答は `Cache-Control: private, no-store`。索引を用意できないときは `503`。

### 3.1 再生リスト `/api/catalog/playlists`

再生リストを探す・ゲームタイトル詳細の「関連する再生リスト」・チャンネル詳細の「再生リスト一覧」で使う。

| パラメータ | 内容 |
|---|---|
| `q` | キーワード（§4.1）。照合先はゲームタイトル・未確定のゲーム名（`gameHint`）・チャンネル名。再生リスト自身のタイトルは対象外（探す仕様書 §4.2） |
| `tags` | タグIDのカンマ区切り。**すべて**付いている再生リストだけ（探す仕様書 §4.3） |
| `sort` | `score`（既定）・`mylist`・`newest`（§4.2） |
| `page` | 1から。範囲外は最後のページ |
| `gameId` / `channelId` | そのゲームタイトル・チャンネルの再生リストだけ |

応答: `items`（カード20件分）・`total`（条件に合う件数）・`page`・`pageCount`・`totalVideoCount`（条件に合う再生リストの動画数の合計。詳細ページの「N 動画」）。

### 3.2 チャンネル `/api/catalog/channels`

チャンネル名から探すで使う。掲載中の再生リストが1件以上あるチャンネルだけ（チャンネル 探す 仕様書 §9.1）。

| パラメータ | 内容 |
|---|---|
| `q` | キーワード（チャンネル名） |
| `sort` | `playlistCount`（既定）・`name`・`videoCount`。同数はチャンネル名順（§5.2） |
| `page` | 1から |

各チャンネルの再生リスト数・動画数・ピックアップ（スコア上位3件）は、掲載中の再生リストから集計する。

### 3.3 ゲームタイトル `/api/catalog/games`

ゲームタイトルから探すで使う。ゲームタイトルは全件が対象（掲載中の再生リストが0件のものも出す。今のまま）。

| パラメータ | 内容 |
|---|---|
| `q` | キーワード（ゲームタイトル名） |
| `genres` | ジャンルIDのカンマ区切り。**どれか**に当てはまるもの（ゲームタイトル 探す 仕様書 §4.3） |
| `tags` | タグIDのカンマ区切り。**すべて**付いているもの（§4.4） |
| `sort` | `playlistCount`（既定）・`title`・`videoCount`。同数はタイトル名順（§5.2） |
| `page` | 1から |

再生リスト数・動画数は掲載中の再生リストだけで数える（`games.playlistCount` の値には頼らない。ゲームタイトル 探す 仕様書 v1.5）。

### 3.4 TOP `/api/catalog/top`

TOP の再生リストのセクション（ページ top 仕様書 §6・§7・§8）。カードは `playlists` に1回ずつ入れ、各セクションは ID の並びで返す。

| セクション | 返す内容 |
|---|---|
| 注目の再生リスト（§6） | スコアのある再生リストをスコアの高い順に、「総合」とジャンルごと（`gameGenreIds`）に**最大40件ずつ**。画面側でログイン中のユーザーの完走済みを除いてから**最大20件**を出す（除いた分の補充はしない、§6.4） |
| 新着の再生リスト（§7） | 登録日（`registeredAt`）の新しい順に最大20件 |
| タグピックアップ（§8） | 使用数（`usagePlaylistCount`）の多いタグ上位6件のうち掲載中の再生リストがあるもの。各タグはスコアの高い順（スコアなしは末尾）に最大20件 |

### 3.5 回数制限

一覧 API はログイン不要のため、連打でサーバーの CPU を使い切られないよう、回数を制限する（`lib/rate-limit.ts`）。

| 項目 | 内容 |
|---|---|
| 接続元ごとの上限 | 1分間に240回（約4回/秒）。人が普通に使う量（キーワードを打ちながらの検索は300msのデバウンス、ページ送り）には当たらない |
| インスタンス全体の上限 | 1分間に3,000回。接続元の特定をすり抜けて送られた場合の歯止め |
| 接続元の見分け方 | Firebase Hosting が付ける `fastly-client-ip`（利用者が偽装できない）。無ければ `x-forwarded-for` の先頭 |
| 超えたとき | `429` と `Retry-After`（秒）を返す。画面は「一覧を読み込めませんでした」と再読み込みのボタンを出す（§5.3）。1分で数え直し |
| 数え方 | Cloud Run のインスタンスごとのメモリ（外部の保存先は使わない）。インスタンスが増えるとその分だけ通る数も増えるが、一覧は索引を引くだけで安いため、1人の連打で CPU が埋まることを防ぐには足りる。厳密な制限が要るようになったら Cloud Armor などを検討する |

## 4. 検索のきまり

### 4.1 キーワード

| 項目 | 内容 |
|---|---|
| 一致のしかた | 部分一致 |
| 無視する違い | 大文字・小文字、全角・半角（Unicode の NFKC 正規化）、カタカナ・ひらがな（例: 「どらくえ」で「ドラクエ」が当たる） |
| 空白 | 空白で区切った語が**すべて**含まれるもの（語ごとに別の項目に当たってもよい。例: 「マリオ キヨ」でゲームタイトルに「マリオ」・チャンネル名に「キヨ」を含む再生リスト） |
| 長さ | 最大100文字（超えた分は使わない） |
| 入力のタイミング | 入力が止まってから300ms後に検索する（探す仕様書 §4.2 のデバウンス）。待っている間と読み込み中は、前の結果を薄く表示したままにする |

### 4.2 並び順

ページをまたいで並びが入れ替わらないよう、同じ値どうしは最後に登録日の新しい順・ID順で必ず順番を決める。

| `sort` | 並び |
|---|---|
| `score` | スコアの高い順（評価なしは末尾）→ マイリスト登録者数の多い順 |
| `mylist` | マイリスト登録者数の多い順 → スコアの高い順 |
| `newest` | 最新の動画の投稿日（`latestVideoPublishedAt`）が新しい順（無いものは末尾） |

## 5. 画面側

### 5.1 ページ送り

1ページ20件。ページ番号は、ページが多いとき（7ページ超）は最初・最後・今のページの前後だけを出し、間は「…」で省く（例: `1 … 49 50 51 … 265`）。スマートフォン幅（390px）でも1行に収まる。

### 5.2 件数・空状態

件数（「XX件」）はサーバーが返す `total`。0件のとき、検索条件が無ければ「まだ登録されていません」、あれば「見つかりませんでした」（各仕様書の空状態）。

### 5.3 読み込めなかったとき

API が失敗したときは、一覧の位置に「一覧を読み込めませんでした。時間をおいてもう一度お試しください。」と「再読み込み」ボタンを出す。TOP では再生リストのセクションを出さない（ヒーロー・マイリストは出す）。

## 6. 対象外

- 取り下げ中のまとめ機能（`/collections`・まとめの再生リスト選択。`COLLECTIONS_ENABLED` が false の間は開けない）は、今の全件取得のまま残す。まとめを戻すときにサーバー側検索へ載せ替える。
- 検索条件の URL への同期（今もしていない）。
- チャンネルの「人気順」（段階5）。
