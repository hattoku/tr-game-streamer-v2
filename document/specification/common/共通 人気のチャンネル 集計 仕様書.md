## 1. 概要

リブランディング段階5。TOPの「人気のチャンネル」とチャンネル一覧の「人気順」に使う、チャンネルの人気の数字を決める。

| 項目 | 決めたこと（2026-11-08 ユーザー決定） |
|---|---|
| 基準 | YouTube の登録者数・再生数は使わず、**プレミテのユーザーの行動**を合算する |
| 対象 | そのチャンネルの**掲載中**（公開かつ `listingStatus == 'listed'`）の再生リスト |
| 数えるもの | マイリストに入れた人数・レビューを書いた人数・視聴を始めた人数 |
| 水増しの防止 | 同じ人は何度押しても1人として数える |
| 期間 | 累計に、直近30日の分を加点する |
| 運営のピン留め | 運営がチャンネルをピン留めすると、数字に関係なく先頭に出す（友人テスト直後は数字がほぼゼロのため） |
| 重み | 仮の値。友人テストの結果を見て直す |
| 計算のしかた | 表示のたびに数えず、**定期的に集計してチャンネルの文書に保存する** |

## 2. 数え方

### 2.1 3つの数

いずれも、**チャンネルごとに、同じ人は1人**として数える（そのチャンネルの再生リストを3つマイリストに入れた人も、マイリストの数は1人）。

| 数 | 数える人 | 「直近30日」の基準日 |
|---|---|---|
| マイリストの人数 | そのチャンネルの掲載中の再生リストを、今マイリストに入れている人（`mylist`）。外した人は数えない | マイリストに入れた日（`mylist.createdAt`）。複数あれば一番新しい日 |
| レビューの人数 | そのチャンネルの掲載中の再生リストにレビューを書いている人（`reviews`）。通報で非表示（`isHidden`）のレビューは数えない | 最初に投稿した日（`reviews.postedAt`）。複数あれば一番新しい日 |
| 視聴を始めた人数 | そのチャンネルの掲載中の再生リストの動画を再生したことがある人（§2.3 の `playlist_viewers`） | 初めて再生した日（`playlist_viewers.firstWatchedAt`）。複数あれば一番新しい日 |

> 「直近30日」は集計した時点から30日前まで。1人がある再生リストを40日前に、別の再生リストを10日前にマイリストに入れたなら、その人は「直近30日」にも入る（最近そのチャンネルに興味を持った人として数える）。

### 2.2 人気の点数

```
人気の点数 = Σ（数の種類ごと）重み × （累計の人数 ＋ 直近30日の加点 × 直近30日の人数）
```

| 定数（仮） | 値 | 置き場所 |
|---|---|---|
| マイリストの重み | 1 | `lib/popularity-shared.ts` の `POPULARITY_WEIGHTS` |
| レビューの重み | 1 | 同上 |
| 視聴を始めた人の重み | 1 | 同上 |
| 直近30日の加点 | 1（直近30日の人は2人分になる） | `RECENT_BONUS` |
| 直近の日数 | 30日 | `RECENT_DAYS` |

重みを変えたときは、次の集計（§3）で全チャンネルの点数が新しい式で入れ替わる（保存しているのは人数なので、点数を読み直すだけで足りる。§4）。

### 2.3 視聴を始めた人の記録（`playlist_viewers`）

視聴の記録（`watch_history`）は動画ごとに1件で、本人が視聴履歴の画面から消せる。そのまま数えると、件数が多く、消した人の分が減ってしまう。そこで集計のたびに、**前回の集計より後に増えた・更新された `watch_history` だけ**を読み、「この人はこの再生リストを見始めた」という記録を `playlist_viewers/{userId}_{playlistId}` に1件だけ作る。

| 項目 | 内容 |
|---|---|
| 作るとき | `watch_history.watchedAt` が前回の集計の時刻（5分の重なりを持たせる）より後の記録に、まだ `playlist_viewers` が無い組み合わせがあったとき |
| `firstWatchedAt` | その組み合わせで見つかった `watchedAt` のうち一番古いもの。一度作ったら変えない |
| 消すとき | 消さない（視聴履歴を消しても「見始めた」事実は残す）。退会の削除（データモデル設計書 §7.1）には含める |
| 初回 | 前回の集計の時刻が無いときは `watch_history` を全件読む（それまでの視聴をまとめて取り込む） |
| 書き込み・読み取り | サーバー（Admin SDK）だけ。クライアントからは読み書きできない（rules の既定の拒否） |

## 3. 集計の実行

| 項目 | 内容 |
|---|---|
| API | `POST /api/admin/popularity/recompute`。管理者のログイン（Bearer）か、Cloud Scheduler の `X-Cron-Secret` が `CRON_SECRET` と一致すること（新着動画の取得と同じ方式） |
| 定期実行 | Cloud Scheduler で**毎日 4:00（日本時間）**（「直近30日」が日ごとにずれるため毎日）。ジョブ名 `channel-popularity-daily` |
| 手動実行 | 管理画面の掲載チャンネル（`/admin/collection/channels`）の「人気の数字を今すぐ集計する」 |
| 処理の流れ | ① 公開かつ掲載中の再生リストのチャンネルを読む → ② `playlist_viewers` を増やす（§2.3）→ ③ `mylist`・`reviews`・`playlist_viewers` を読み、チャンネルごとに同じ人を1人にして数える → ④ 数が変わったチャンネルだけ `channels.popularity` を書く（数が0になったチャンネルも0で書き直す）→ ⑤ `batch_state/channel_popularity` に今回の時刻を、`batch_logs` に結果を残す |
| 読み取り量 | `mylist`・`reviews`・`playlist_viewers` は毎回全件（必要な項目だけ）。`watch_history` は前回より後の分だけ。利用者が増えて重くなったら、変わった分だけ数え直す形に変える |
| 同時に走ったとき | 2回目は結果が同じになるだけで壊れない（人数を数え直して上書きするため） |
| 失敗したとき | `batch_logs` に `status: "error"` を残し、500 を返す。保存済みの数字はそのまま使われる |

`batch_logs` には `functionName: "channel_popularity"`、`processedCount`（集計したチャンネル数）、`updatedChannelCount`（数字を書き直したチャンネル数）、`newViewerCount`（新しく作った `playlist_viewers` の数）、`quotaConsumed: 0` を残す。

## 4. 保存する形（`channels.popularity`）

| フィールド | 内容 |
|---|---|
| `mylistUsers` / `reviewUsers` / `viewerUsers` | 累計の人数（§2.1） |
| `recentMylistUsers` / `recentReviewUsers` / `recentViewerUsers` | 直近30日の人数 |
| `computedAt` | 集計した日時 |

点数（§2.2）は保存せず、読むたびに人数から計算する（重みを変えたらすぐに反映するため）。`popularity` が無いチャンネルは全部0として扱う。

## 5. 並べ方

TOP の「人気のチャンネル」とチャンネル一覧の「人気順」は同じ並べ方を使う（サーバー側検索の索引で並べる。共通 一覧のサーバー側検索 仕様書 §3.2・§3.4）。

1. **ピン留めしたチャンネル**（`exploration_channels.featuredOrder` に数字があり、`status == 'active'`）を、数字の小さい順に先頭へ。
2. 残りは**人気の点数の高い順**。
3. 同じ点数は、掲載中の再生リストの多い順 → チャンネル名順。

対象は、これまでどおり掲載中の再生リストが1件以上あるチャンネルだけ。ピン留めの変更は数秒以内に反映する（索引が `exploration_channels` も購読する）。点数は集計（§3）のたびに変わる。

---

## 6. 画面に出すもの

- 一般ユーザーの画面には、人気の点数・人数を**出さない**（チャンネルの点数に見えるため。リブランディング検討 項目2）。並び順にだけ使う。
- 管理画面の掲載チャンネル（登録済みの行）には、ピン留めの入力と、人気の点数・内訳（累計／直近30日）・最後に集計した日時を出す（重みを直すときの材料）。
