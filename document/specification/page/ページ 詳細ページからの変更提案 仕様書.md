## 1. 目的

運営が気づかない間違いを、見ている人が見つけて知らせられるようにする。みんなで作る wiki のような世界観に合わせ、気づいた人がその場で伝えられる入口を用意する。ただし、ゲームの情報や掲載の判断は散らかりやすいため、反映する前に運営が確認する。

想定する場面（チケットより）:

| 対象 | 場面 |
|---|---|
| ゲーム詳細 | ゲームタイトル名・ジャンルなどが間違っている。同じゲームが二重に登録されている |
| チャンネル詳細 | もうゲーム実況をやめていて、掲載が合わない。切り抜き・転載のチャンネルだった |
| 再生リスト詳細 | ゲーム実況と関係ない再生リストが掲載されている。付いているゲームが違う |

本人・事務所からの掲載停止は、これまでどおりお問い合わせで受ける（§5.3）。

## 2. 決まったこと（要約）

| # | 項目 | 決定 |
|---|---|---|
| 1 | 反映のしかた | 審査ワークフローに入り、運営が承認すると反映する |
| 2 | 入口 | 各詳細ページのボタンから、その場の小さな画面（モーダル）で書く。ページは離れない |
| 3 | ゲーム詳細 | 違う項目を選び、正しい内容をひと言書く。運営は編集画面で直してから承認する |
| 4 | チャンネル詳細 | 視聴者からの報告だけを受ける。モーダルの中に小さく本人・事務所向けの案内を出し、お問い合わせへつなぐ |
| 5 | 再生リスト詳細 | 「ゲームが違う」のときは正しいゲームを一覧から選んでもらい、承認するとそのまま付け替える |
| 6 | 誰が・どれくらい | ログインした人だけ。1人1日5件まで。同じ人が同じ対象に重ねて出すことはできない。別の人の報告は受け付け、運営画面で1件にまとめて人数を出す |
| 7 | 承認したとき | 理由ごとに、承認ボタン1つで決まった処理が走る。運営は処理を選び直せる |
| 8 | 送った人への見え方 | 提案履歴に並べ、結果が出たら未読で知らせる。まとめた報告は、報告した全員に知らせる |

## 3. 共通の入口

### 3.1 ボタン

| 項目 | 仕様 |
|---|---|
| 見た目 | 文字のない「⋯」アイコン（読み上げ名「その他のメニュー」）。押すとメニューが開き、項目「情報の更新を提案する」を押すとモーダルが開く。本当に間違いがあったときの逃げ道なので目立たせない（2026-11-17 ユーザー決定） |
| 文言 | 「情報の更新を提案する」（3ページとも同じ）。「間違いを報告する」のように間違いがある前提に聞こえる言い方は避ける（2026-11-17 ユーザー決定） |
| 置き場所 | 各ページの基本情報の枠の右上（§4〜§6 の図）。タグの操作（✎・＋タグを追加）と取り違えないよう離して置く。PC・モバイルとも同じ位置 |
| 誰に出すか | 一般ユーザーと未ログインの人に出す。管理者（owner／operator）には出さない（管理者は直接直せるため。ゲーム詳細では今どおり「ゲームタイトル情報を編集する」を出す） |
| 未ログインで押したとき | 既存のログイン案内モーダル（LoginRequiredModal）を出す（見出し「情報の更新を提案するにはアカウントが必要です」。本文と戻り先は共通 uiコンポーネント フロント 仕様書 §5.2・§5.3。アカウント作成・ログイン後はこの詳細ページへ戻す。v1.2） |
| 出さない場面 | 管理者のとき。対象が提案を受け付けない状態かどうかは送信時にサーバーで確かめる（§7.2） |

### 3.2 モーダルの共通の形

```
┌ 情報の更新を提案する ──────────────── × ┐
│ 対象: [サムネ] {名前}                                        │
│                                                              │
│ 何が違いますか？                                              │
│  ○ 選択肢1                                                   │
│  ○ 選択肢2  …                                                │
│  （選んだ内容によって追加の入力が出る）                       │
│                                                              │
│ 補足（任意／必須）                                            │
│ ┌──────────────────────────────────────────┐ │
│ │                                                          │ │
│ └──────────────────────────────────────────┘ │
│ 運営が確認してから反映します。結果は提案履歴でお知らせします。 │
│                                                              │
│                                   [キャンセル] [提案する]     │
└──────────────────────────────────────────────┘
```

| 項目 | 仕様 |
|---|---|
| 補足 | 500文字まで。必須かどうかは選択肢ごとに決める（§4〜§6） |
| 送信ボタン | 必須の入力がそろうまで押せない。送信中は押せない |
| 送れたとき | モーダルを閉じ、トースト「提案を受け付けました。結果は提案履歴でお知らせします」 |
| 送れなかったとき | モーダルの中にエラーを出す（§7.3 の文言） |
| 再表示 | 自分の提案が審査中の対象では、モーダルを開くと選択肢の代わりに「この{対象}への提案は確認待ちです」と「提案履歴を見る」を出す |

## 4. ゲーム詳細

### 4.1 置き場所

```
┌ ドラゴンクエストIV 導かれし者たち ─────────────────── ⋯ ┐
│ [パッケージ画像]  ジャンル：RPG                              │
│                   テーマ：オーソドックスRPG                  │
│                   □ 1 再生リスト  ▶ 7 動画                   │
│                   タグ [＋ タグを追加]                       │
│                   説明文…                                    │
│ [楽天ブックスで見る]                                         │
└─────────────────────────────────────────┘
```

### 4.2 モーダルの中身

「違う項目」は複数選べる（チェックボックス）。

| 選択肢 | 補足 |
|---|---|
| ゲームタイトル名 | — |
| ジャンル | — |
| テーマ | — |
| 機種 | — |
| パッケージ画像 | — |
| 説明文 | — |
| 同じゲームが二重に登録されている | 選ぶと「もう一方のゲーム」をゲーム選択（既存のゲームタイトル選択モーダル）で選べる（任意） |
| その他 | — |

- 補足は**必須**。案内文は「正しい内容を書いてください（例: 正しくは『ドラゴンクエストIV 導かれし者たち』（PS版）です）」。
- 送るもの: 選んだ項目（複数）、補足、二重登録の相手のゲーム（あれば）。

### 4.3 承認したとき

自動の処理はない。運営が編集画面（管理者の「ゲームタイトル情報を編集する」）で直してから承認する（§8.3）。

## 5. チャンネル詳細

### 5.1 置き場所

チャンネル情報の枠の右上に「⋯」を置く。「YouTubeで見る」「再生リストを追加する」より控えめにする。

### 5.2 モーダルの中身

| 選択肢 | 補足 |
|---|---|
| もうゲーム実況をしていない | 任意 |
| 実況者本人・公式のチャンネルではない（切り抜き・転載など） | 任意 |
| その他 | **必須** |

### 5.3 本人・事務所の方への案内（モーダルの中だけ）

選択肢の下に、小さな枠で出す。チャンネル詳細ページそのものには出さない（実況者・事務所の方へ 仕様書 §3 の決定を維持）。

> ご本人・事務所の方へ: 掲載を止めたい場合は、お問い合わせからお知らせください。確認でき次第、掲載を止めます。
> 「掲載についてお問い合わせ →」（`/contact?type=channel_listing`）

- この案内は未ログインでも見られるよう、未ログインの人がボタンを押したときのログイン案内モーダルにも同じ1行を添える。

### 5.4 承認したとき

既定の処理は「掲載から外す」（掲載チャンネル画面の「掲載から外す」と同じ。`exploration_channels.status` を `excluded` にし、そのチャンネルの再生リストをすべて `channel_off` にする。あとで「掲載する」で戻せる）。

## 6. 再生リスト詳細

### 6.1 置き場所

基本情報セクション（タイトル・スコア・タグ）の右上。

```
┌─────────────────────────────────┐
│ 再生リストのタイトル              ⋯ │
│ ★★★★★ 4.5 / 5                      │
│ マイリスト: 234 | レビュー: 89      │
│ タグ [ジャンル1] [ジャンル2] ✎      │
└─────────────────────────────────┘
```

### 6.2 モーダルの中身

| 選択肢 | 追加の入力 | 補足 |
|---|---|---|
| ゲーム実況の再生リストではない | — | 任意 |
| 複数のゲームが混ざっている | — | 任意 |
| 付いているゲームが違う | 「正しいゲーム」をゲーム選択（既存のゲームタイトル選択モーダル）で選ぶ。一覧に無いときは「一覧に無いゲームを入力する」でゲーム名を書く（どちらか必須） | 任意 |
| その他 | — | **必須** |

- ゲーム未設定の再生リストでは「付いているゲームが違う」は出さない（今ある「ゲームを登録」とゲームの提案を使う）。
- 今付いているゲームと同じゲームは選べない。

### 6.3 承認したとき

| 選択肢 | 既定の処理 |
|---|---|
| ゲーム実況の再生リストではない | 掲載状態を「ゲームではない」（`non_game`）にする。さがすから外れる |
| 複数のゲームが混ざっている | 掲載状態を「対象外」（`excluded`）にする。さがすから外れる |
| 付いているゲームが違う | 選ばれたゲームに付け替える（管理者の付け替えと同じ。履歴 `playlist_game_changes` に残る）。ゲーム名を書いた提案は、運営がゲームを決めてから（既存から選ぶ／新しく登録する。ゲームタイトル提案の審査と同じ枠）承認する |
| その他 | 自動の処理なし（運営が手で直してから承認） |

- 掲載状態の変更は管理者の操作と同じ扱い（`listingSetBy: admin`、`listingReason: report`）にし、自動の判定し直しで上書きしない。
- 承認後に戻したくなったら、自動掲載の確認画面（収集候補レビューUI仕様書 §8）の該当タブから今までどおり戻せる。

## 7. 受け付けのルール

### 7.1 回数と重複

| 項目 | 仕様 |
|---|---|
| 送れる人 | ログイン済みの一般ユーザー（管理者も API 上は送れるが、ボタンは出さない） |
| 回数 | 1人あたり直近24時間に5件まで（3種類の合計） |
| 同じ人の重複 | 同じ人が、同じ対象に審査中の提案を持っている間は送れない |
| 別の人 | 送れる。運営画面で対象ごとに1件にまとめ、人数を出す（§8.1） |

### 7.2 受け付けない対象

| 対象 | 受け付けない状態 | ボタン |
|---|---|---|
| 再生リスト | 掲載中（`isPublic` かつ `listed`）でない | 出さない（そもそも詳細ページが 404） |
| チャンネル | 掲載チャンネル（`active`）でない | 出す（`exploration_channels` はクライアントから読めないため）。送信すると「このチャンネルは今、提案を受け付けていません」 |
| ゲーム | 無し | — |

### 7.3 エラーの文言

| 場面 | 文言 |
|---|---|
| 1日の上限 | 「提案は1日5件までです。時間をおいてお試しください」 |
| 自分の提案が審査中 | 「この{対象}への提案は確認待ちです」＋「提案履歴を見る」 |
| 対象が受け付けない状態になった | 「この{対象}は今、提案を受け付けていません」 |
| 通信エラー | 「通信エラーが発生しました。時間をおいて再試行してください」 |

## 8. 運営側（審査ワークフロー）

### 8.1 一覧

- 審査ワークフロー一覧の「通報」セクションに、新しい種別「変更の提案」として並べる（レビュー通報と同じセクション）。
- **対象ごとに1行にまとめる**。行には種別（ゲーム／チャンネル／再生リスト）、対象名、いちばん多い理由、人数（「3人」）、最初の提出日時を出す。
- 未処理件数のバッジ（ユーザーメニュー・審査ワークフロータブ）は、まとめた行の数で数える。

### 8.2 詳細

- 対象の概要（サムネ・名前・詳細ページへのリンク。再生リストは今のゲーム・掲載状態、チャンネルは掲載状態と再生リスト数）。
- 報告の一覧: 報告した人（表示名）・選んだ理由・補足・二重登録の相手／正しいゲーム・日時。
- 処理の選択（§6.3・§5.4 の既定の処理が最初から選ばれている。理由が分かれているときはいちばん多い理由の処理）。選び直せる処理:

| 対象 | 選べる処理 |
|---|---|
| 再生リスト | ゲームではないにする／対象外にする／ゲームを付け替える（ゲームを選ぶ）／処理なし（手で直した） |
| チャンネル | 掲載から外す／処理なし（手で直した） |
| ゲーム | 処理なし（編集画面で直した）のみ。「編集画面を開く」（ゲーム詳細を新しいタブで開く）を添える |

- 「承認する」で選んだ処理を実行し、**その対象への審査中の提案をすべて承認済みにする**。「却下する」も同じくまとめて却下する。
- 承認・却下の確認ダイアログ、運営メモ、同時承認の防止（`approvingAt`）は他の種別と同じ（管理 審査ワークフロー仕様書 §3.2・§3.3）。

### 8.3 見送り理由（定型）

却下のときは次から1つを必須で選ぶ。提案した人への通知と提案履歴にそのまま出す。任意の自由記述は運営内部向け。

1. 確認しましたが、今の内容で合っていました
2. すでに直っています
3. 内容を確かめられませんでした
4. その他（掲載の基準に合わせて判断しました）

## 9. 送った人への見え方

### 9.1 提案履歴（`/playlists/proposals`）

- 再生リスト提案・チャンネル申請と同じ一覧に「変更の提案」のカードを並べる（提案日時の新しい順）。
- カード: 対象の種別ラベル（ゲーム／チャンネル／再生リスト）、対象のサムネ・名前（詳細ページへのリンク。外れた再生リストはリンクなし）、選んだ理由、提案日時、状態（確認待ち／反映済み／見送り＋定型の理由）。
- 運営メモ・内部向けの自由記述は出さない（今の提案履歴と同じく API で項目を絞る）。

### 9.2 結果のお知らせ

- 承認・却下のとき、報告した**全員**にサイト内通知（種別「審査結果」`review_result`）を作る。出し方は今の審査結果と同じ（通知一覧・ベルには出さず、ユーザーアイコンの件数と「提案履歴　未読N」。提案履歴の「新しい審査結果」とカードの赤丸）。
- 文面:
  - 承認: 「{再生リスト／チャンネル／ゲーム}「{名前}」への提案を反映しました。ありがとうございます」
  - 却下: 「{再生リスト／チャンネル／ゲーム}「{名前}」への提案は見送りになりました（{定型の理由}）」
- 遷移先はどちらも提案履歴。

## 10. データと API

### 10.1 `workflows`

1人の提案を1件のドキュメントにする（まとめは表示のときに行う）。種別は審査ワークフロー仕様書 §3 の名前を使う。

| 種別（`type`） | 対象 |
|---|---|
| `game_title_edit` | ゲーム（既存の種別名。今まで投稿経路が無かった） |
| `channel_report` | チャンネル（新規） |
| `playlist_report` | 再生リスト（既存の種別名。今まで投稿経路が無かった） |

`reportData` に持つもの:

| フィールド | 内容 |
|---|---|
| `targetType` | `game`／`channel`／`playlist` |
| `targetId` | 対象のID（チャンネルは `channels` のID） |
| `targetKey` | `"{targetType}:{targetId}"`（同じ対象の提案をまとめて引くため。等価条件で読む） |
| `targetName` | 提案時点の名前（あとで消えても履歴に出せるように） |
| `targetThumbnailUrl` | 提案時点のサムネ |
| `reason` | 選んだ理由（ゲームは `fields` に複数） |
| `fields` | ゲームのみ。選んだ項目の配列 |
| `detail` | 補足（500文字まで、null 可） |
| `duplicateGameId`／`duplicateGameName` | ゲームのみ。二重登録の相手（任意） |
| `proposedGameId`／`proposedGameName`／`proposedGameTitle` | 再生リストの「ゲームが違う」のみ。選んだゲーム、または書いたゲーム名 |
| `currentGameId`／`currentGameName` | 再生リストの「ゲームが違う」のみ。提案時点のゲーム |
| `decisionId`／`rejectReasonCode` | 審査で書く（上の段落） |

承認・却下のときは、まとめた全件の `step2History` に同じ記録（`action`: `approved`／`rejected`、`approveAction`: `non_game`／`excluded`／`relink`／`channel_excluded`／`none`、付け替えたゲームの `gameId`・`gameName`）を足し、`reportData.decisionId`（操作した提案のID）と、却下なら `reportData.rejectReasonCode` を書く。まとめるのは承認・却下を押した時点までに届いた提案だけ（処理中に届いた提案は審査中に残す）。

### 10.2 API

| API | 内容 |
|---|---|
| `POST /api/change-proposals` | 提案を送る。`requireUser`。§7 の判定（回数・重複・対象の状態）をサーバーで行う。クライアントから `workflows` に直接書かない |
| `GET /api/change-proposals/mine?targetKey=` | 詳細ページでモーダルを開いたとき、自分の審査中の提案があるか |
| `GET /api/playlists/proposals` | 今の提案履歴 API に「変更の提案」を足す |
| `PATCH /api/admin/workflows/{id}` | 今の承認・却下 API に3種別を足す。同じ `targetKey` の審査中のものをまとめて処理する |

- 掲載状態の変更は `lib/listing-server.ts` の `unlistPlaylist`、チャンネルは `turnChannelOff(…, 'channel_excluded')`、付け替えは `lib/playlist-game-linking.ts`（管理者の付け替えと同じ処理）を使う。
- インデックス: `workflows` の `reportData.targetKey` の等価条件と `submittedBy`＋`type` の等価条件で読み、状態や日付はメモリで絞る（今の提案系と同じ。複合インデックスを増やさない）。
