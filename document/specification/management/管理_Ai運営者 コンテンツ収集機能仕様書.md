## 1. 概要

> **リブランディング（v4.0、2026-11-01 決定）**: プレミテは「ゲーム起点の再生リスト格付け」から「**認定チャンネル（運営が認めた実況者のチャンネル）の再生リストのキュレーション**」に考え方を改めた（プレミテ企画書 §0.0）。これに合わせ、収集の品質の関門を「再生リスト1件ずつの承認」から「**チャンネルを認定するかどうか**」に移す。新しい仕組みは **第10章** で定める。
> - 第10章は実装の段階4（収集の変更）で実装する。それまでは第2章・第3章（探索 → 収集候補 → まとめて承認）が今の動作であり、段階4の実装で第10章に置き換える（第3章のうち §3.1 のチャンネルの特定・§3.4 のゲーム推定・§3.5 のタグ候補は第10章でもそのまま使う）。
> - 「認定チャンネル」は社内・仕様書上の呼び名で、**お客様から見える画面には出さない**（画面上は「チャンネル」「人気のチャンネル」などと表現する）。
> - 決定の全文: プロジェクトファイル `plans/チャンネル起点運用/リブランディング-検討項目.md`（決定ログ）、精査: 同フォルダ `チャンネル起点運用-精査と方針案.md`。

本仕様書は、プレミテへの登録候補となる再生リストを自動で集める機能の設計を定義する。

v3.0（2026-10-26）で、収集の起点を**有名実況チャンネル**に変更した。友人テストの前に再生リスト・ゲームタイトル・タグを揃えるため、Gemini による品質判定を含まない**最小版**を先に実装する。

| 機能 | 状態 | 概要 |
|------|------|------|
| チャンネル起点の再生リスト探索 | **実装対象（v3.0）** | 運営が登録した「探索対象チャンネル」の再生リストを一括取得し、機械的なしぼり込みのうえ収集候補として保存する |
| 新作タイトル検知バッチ | 将来実装 | 楽天ブックスの新着・売れ筋からマスタ未登録のゲームタイトルを検知する |
| ゲームタイトル起点の補助収集 | 将来実装 | チャンネル起点で拾えないゲームを、ゲームタイトル名の YouTube 検索で補う |
| Gemini による品質スクリーニング | 将来実装 | 実況シリーズらしさ・更新継続性・スパムの判定 |

収集されたコンテンツの最終的な掲載可否は常に管理者が判断する（自動で公開はしない）。
> v4.0 の第10章では、認定チャンネルごとに「自動で掲載／確認してから掲載」を選べるようにする（既定は「確認してから掲載」）。「自動で掲載」にしたチャンネルでは、ルールの判定を通った再生リストを管理者の確認なしで掲載する。

### 1.1 チャンネル起点に変更した理由

- **クォータ**: ゲームタイトル名での検索（`search.list`）は1回100ユニットかかる。チャンネルの再生リスト一覧（`playlists.list` の `channelId` 指定）は50件ごとに1ユニットで済み、数十分の一のコストで済む。
- **量**: 有名実況者のチャンネルには実況シリーズが数十本単位で並んでおり、少ない操作で数を揃えられる。
- **品質**: 実績のある実況者単位で選ぶため、スパムや無関係な動画が混ざりにくい。
- **ゲームタイトルとの関係**: 再生リストのタイトルからゲームを推定し、マスタに無いゲームは承認時にその場で登録する。ゲームタイトルが先に揃っていなくても再生リストを集められ、ゲームタイトルも一緒に増える。

### 1.2 網羅の基準

友人テスト前は「ゲーム実況者 @ ウィキ」（https://w.atwiki.jp/gameplayer/ ）に掲載されている実況者を最低限すべて探索対象にする。掲載名の一覧（2026-10-25 時点で80件）を初期データとし、足りない分は管理者が追加する。wiki の文章は使わず、チャンネルを特定するためだけに使う。

## 2. 全体アーキテクチャ

```
【探索対象チャンネルの登録】（管理画面）
  名前をまとめて追加（1行1件）／チャンネルURL・@ハンドルを直接指定
    ↓
  名前の場合: search.list（type=channel）で候補を最大5件取得（100ユニット/件）
  URL・ハンドルの場合: channels.list で直接特定（1ユニット/件）
    ↓
  管理者が候補から正しいチャンネルを選んで確定（または除外）
  チャンネル単位のタグ（実況スタイル系など）を設定

【チャンネル起点の再生リスト探索】
  管理画面のボタン／Cloud Scheduler（週1回）→ Cloud Run の API（X-Cron-Secret）
    ↓
  当日のクォータ残量チェック
    ↓
  確定済みチャンネルごとに playlists.list（channelId 指定、50件/1ユニット）
    ↓
  ハードフィルタ（動画数・公開状態・登録済み・候補化済み・除外語）
    ↓
  ゲーム推定（登録済みゲームタイトルとの照合）／タグ候補（チャンネル単位タグ＋タイトルの語句）
    ↓
  collection_candidates に保存（status: pending）
    ↓
  推定なしの候補（未検索のもの）を、楽天ブックスで1件ずつ検索して rakutenSearch に保存（v3.3。
  定期実行は開始から240秒まで・画面のボタンは45秒まで。残りは次の実行か画面の自動検索が拾う。レビューUI §3.7）
    ↓
  管理画面「収集候補」でまとめて承認 → playlists に登録（タグは固定タグとして付与）
```

### 2.1 実行基盤

技術スタック仕様書・AI運営者企画書では Cloud Functions を想定していたが、Cloud Functions 基盤はまだ導入していない。既存の新着動画取得（`/api/admin/refresh-new-videos`）と同じく、**Cloud Run 上の API Route を Cloud Scheduler から `X-Cron-Secret` 付きで呼ぶ**構成とする。管理画面のボタンからは管理者の ID トークンで同じ API を呼ぶ。

## 3. チャンネル起点の再生リスト探索（実装対象）

### 3.1 探索対象チャンネル

`exploration_channels` コレクション（Firestore データモデル設計書 §3.32）で管理する。

| 状態（`status`） | 意味 |
|------|------|
| `unresolved` | 名前だけ登録された状態。YouTube のチャンネルは未特定 |
| `pending_confirm` | 名前で検索し、候補（最大5件）が付いた状態。管理者の確認待ち |
| `active` | チャンネルが確定し、探索の対象になっている |
| `excluded` | 管理者が除外した（ゲーム実況中心でない、見つからない等）。探索しない |

- **名前からの特定**: `search.list`（`type=channel`、`maxResults=5`、`regionCode=JP`、`relevanceLanguage=ja`）で候補を取り、`channels.list` で登録者数・アイコンを補う。1件あたり約101ユニットかかるため、管理画面からは**1回あたりの件数上限（既定40件）**を設けて実行する。80件なら2日に分けて実行する。
- **URL・ハンドルからの特定**: `https://www.youtube.com/@handle`・`https://www.youtube.com/channel/UC...`・`@handle`・`UC...` を受け付け、`channels.list`（`forHandle` または `id`）で直接特定する（1ユニット）。名前検索で正しい候補が出なかった場合の手段にもなる。
- **重複**: 同じ YouTube チャンネルIDの `active` が既にある場合は確定できない。
- **チャンネル単位のタグ**: タグマスタのうち運営者タグ（`origin: operator`）から選ぶ。そのチャンネルの再生リストを承認するときに付与する。

### 3.2 探索の実行

| 項目 | 仕様 |
|------|------|
| 実行契機 | 管理画面「収集候補」の「探索を実行」ボタン／Cloud Scheduler（週1回） |
| 対象 | `status: active` の探索対象チャンネル全件（ボタン実行時は特定チャンネル1件だけの実行も可） |
| 取得 | `playlists.list`（`part=snippet,contentDetails,status`、`channelId`、`maxResults=50`）をページ送りで全件 |
| 差分 | 既に `collection_candidates` にある再生リスト（どの状態でも）・`playlists` に登録済みの再生リストは保存しない。週1の再実行では新しく作られた再生リストだけが候補に入る |
| 記録 | 探索対象チャンネルの `lastExploredAt`・`lastFoundCount` を更新し、1回の実行結果を `collection_batch_logs` に記録する |

### 3.3 ハードフィルタ

API で取得できる情報だけで機械的に除外する。除外したものは保存せず、件数だけをログに残す。

| 除外条件 | 理由 |
|---------|------|
| 動画数（`contentDetails.itemCount`）が9本以下 | 友人テスト前は見応えのあるシリーズを優先し、承認の件数を抑える（v3.1 で 2本以下 → 9本以下に変更） |
| 公開状態が `public` 以外 | 視聴できない |
| `playlists` に登録済み | 重複登録の防止 |
| `collection_candidates` に存在する | 候補の重複防止（却下済みを再度候補にしない） |
| タイトルに除外語を含む | 実況シリーズでない可能性が高い |

`collection_candidates` に既にある再生リストは新しい候補にしないが、動画数（`videoCount`）と数えた日時（`videoCountCheckedAt`）はこの探索の値に更新する（v3.2。取得済みの一覧を使うのでクォータは増えない）。

除外語（初期値）: `切り抜き`、`歌ってみた`、`踊ってみた`、`ショート`、`shorts`、`配信アーカイブ`、`生放送`、`メンバー限定`、`ASMR`、`Vlog`、`MV`、`料理`、`単発`（v3.1 で追加。「単発実況」のような寄せ集めの再生リストはシリーズではないため）、`実写`、`くだらない`、`ドッキリ`、`大喜利`、`ラジオ`、`雑談`、`食べてみた`、`飲んでみた`（v3.5 で追加。ゲームではない企画・番組）。「検証」「企画」「やってみた」はゲーム実況でも使うため入れない。大文字・小文字と全角・半角の違いは区別しない。除外語は `lib/exploration-rules.ts` に定数で持ち、運用しながら見直す。

> **除外語に当たった再生リストの扱い（v3.5）**: 捨てずに、候補を「却下済み（自動）」で残す（`reviewedBy: 'auto'`、`reviewComment: 'auto_exclude:<語>'`）。次の探索で同じ判定をやり直さず、却下の一覧に理由が出て「未処理に戻す」こともできる。動画数不足・非公開は後から変わりうるので残さない。

> **配信アーカイブについて**: 生配信の再生リストは1本が数時間に及び、プレミテの「シリーズを順に見る」体験と相性が悪いため初期値で除外する。必要になれば除外語から外す。

### 3.4 ゲームの推定

再生リストのタイトルと、登録済みのゲームタイトル（`games.title`）を照合する。

1. 両方を正規化する（Unicode NFKC、小文字化、空白・記号の除去）。
2. 正規化したゲームタイトルが、正規化した再生リストタイトルに含まれるものを候補とする（2文字以下のタイトルは誤一致を避けるため対象外）。
3. 候補が複数ある場合は、最も長く一致したものを採用する。
4. 一致しない場合は「推定なし」とする。承認画面では、`gameQuery` の名前のままゲームタイトルを登録してまとめて承認できる（管理者が書き換え・既存から選ぶこともできる。収集候補レビューUI仕様書 v2.1 §3.5・§4.3）。あわせて、再生リストタイトルからゲーム名らしい部分（`【】`・`［］`・`「」` で囲まれた部分、なければ「実況」「#」「Part」等より前の部分）を抜き出し、`gameQuery` として保存する。承認画面はこの語句で楽天ブックスを自動で検索する。

推定結果は探索時点のゲームタイトル一覧で計算する。承認画面では、候補保存後に登録されたゲームタイトルでも推定し直す。

### 3.5 タグ候補

承認時に付与するタグを、探索時に候補として計算して保存する。**タグマスタの運営者タグ（`origin: operator`）だけを使い、新しいタグは作らない。**

| 由来 | 内容 |
|------|------|
| チャンネル単位 | 探索対象チャンネルに設定したタグ（例: 生声・男性実況者・ゆっくり・Vtuber） |
| タイトルの語句 | 再生リストタイトルに含まれる語句から対応するタグを付ける。対応表は `lib/exploration-rules.ts` に定数で持つ |

語句とタグの対応（初期値）:

| 語句（いずれかを含む） | タグ |
|------|------|
| 初見 | 初見プレイ |
| 縛り | 縛りプレイ |
| RTA | RTA |
| ノーダメ | ノーダメージ |
| 低レベル | 低レベルクリア |
| 全実績、トロコン、トロフィーコンプ | 全実績解除 |
| やり込み | やり込みプレイ |
| ゆっくり | ゆっくり |
| VOICEROID、ボイロ、ゆかり、琴葉 | VOICEROID |
| ノーカット | ノーカット |
| 字幕 | 字幕・テロップ充実 |
| 協力 | 協力プレイ |
| 対戦 | 対戦メイン |
| 考察 | 考察メイン |
| 攻略 | 攻略メイン |
| 解説 | 解説メイン |
| 二人、2人、三人、3人、4人、複数人、コラボ | 複数人プレイ |

### 3.6 承認

承認の操作と画面は「管理 AI運営者向け収集候補レビューUI仕様書」で定義する。登録処理は管理者用の再生リスト登録（`/api/playlists/register`）と同じ内容で行い、次の点だけが異なる。

- ゲームタイトルは承認時に確定した ID を使う（推定・管理者の選択・その場での新規登録、または推定なしの候補のゲーム名から用意したもののいずれか。後者は既存と正規化で一致すればそれ、無ければ楽天ブックスで一致する商品の情報を入れて新規登録する。収集候補レビューUI仕様書 v2.1 §4.3）。
- チャンネル単位のタグとタイトル由来のタグ（承認時に管理者が外したものを除く）を `playlistTagIds` と `playlistTagsFixed` の両方に入れ、各タグの `usagePlaylistCount` を加算する。**固定タグにする**のは、運営が付けたタグを一般ユーザーが外せないようにするため。
- 候補の `status` を `registered` にし、`reviewedAt`・`reviewedBy`・`registeredPlaylistId` を記録する。

## 4. 新作タイトル検知バッチ（将来実装）

### 4.1 目的

YouTubeのクォータを消費せずに、発売直後の話題タイトルを検知してゲームタイトルマスタを充実させる。v3.0 ではチャンネル起点の探索の承認時にゲームタイトルが増えるため、優先度を下げて友人テストの後に回す。

### 4.2 データソース

楽天ブックスAPIの以下のエンドポイントを利用する。

| エンドポイント | 用途 |
|--------------|------|
| 新着ランキング | 直近の発売タイトルを取得 |
| 売れ筋ランキング | 発売後に話題になっているタイトルを取得 |

対象ジャンル・プラットフォームはプレミテの対象機種（Nintendo Switch / Nintendo Switch 2 / PS5 / PS4）に絞り込む。

### 4.3 処理概要

```
楽天ブックスAPIから新着・ランキングを取得
    ↓
DBのゲームタイトルマスタと突合
    ↓
未登録タイトルのみを候補として抽出
    ↓
Firestoreに new_title_candidates コレクションへ保存
    ↓
オーナーに通知
```

### 4.4 実行タイミング（案）

週1〜2回程度の実行を想定。詳細は実装時に決定する。レビュー画面は実装着手時に別途定義する。

## 5. ゲームタイトル起点の補助収集（将来実装）

v2.0 までの主たる収集方式。v3.0 ではチャンネル起点で拾えないゲームを補う補助に位置づける。

- 1タイトルあたり `{ゲームタイトル名} 実況` で `search.list`（`type=playlist`）を実行する（100ユニット/回）。
- 1日のクォータ（10,000ユニット）を超えないよう、1回の実行で処理するタイトル数に上限を設け、未探索・最終探索が古い順に回す。
- ハードフィルタ・ゲーム推定・保存先は §3 と共通とする。

## 6. クォータ管理方針

- YouTube Data API の1日の上限は 10,000 ユニット。**API キーは本番・stg で共有**している（HANDOFF.md 未解決13）ため、stg での試行は少数のチャンネルに絞る。
- 本機能の消費は `collection_quota_logs/{YYYY-MM-DD}`（日本時間の日付）に積算する。既存の動画更新バッチ（`api_quota_logs`）とは分けて記録する。
- **1日の上限（既定 6,000 ユニット）**を超える操作は実行前に拒否する。既存の新着動画取得の分（最大約2,000ユニット/回）を残すため。
- 消費の目安:

| 操作 | 消費 |
|------|------|
| 名前からチャンネルを特定 | 約101ユニット/件（search.list 100 + channels.list 1） |
| URL・ハンドルからチャンネルを特定 | 1ユニット/件 |
| 探索（1チャンネル） | 再生リスト50件ごとに1ユニット |
| 承認（1再生リスト） | 約 (動画数 ÷ 50) × 2 + 2 ユニット（登録時の動画・長さ取得） |

## 7. 品質スクリーニング設計方針（将来実装）

ハードフィルタを通過した候補に対し、Gemini APIで以下を判定する。詳細な品質基準はAI運営者_コンテンツ品質基準検討書を参照。

| 判定観点 | 内容 |
|---------|------|
| 実況シリーズらしさ | 動画タイトル群からゲーム実況のシリーズと判断できるか |
| 更新継続性 | 直近の投稿から90日以内、または平均投稿間隔の3倍以内か |
| スパム・荒らし | 明らかな不正コンテンツでないか |
| 完結済み | 「最終回」等の語句からシリーズ完結を推測できるか |

`spam` 判定のみ自動除外。その他のフラグ（`update_stopped`・`completed`・`not_gameplay`）は管理者判断に委ねる。AIによるゲームタイトル推定・タグ提案（AI運営者企画書 §4.3）もこの段階で検討する。

## 10. 認定チャンネルの自動掲載（リブランディング後の収集）

> 実装段階: **段階4**（収集の変更）。掲載状態（`listingStatus`）の追加と既存データの移行・検索面の絞り込みは**段階3**で先に入れる（§10.9）。チャンネル申請（§10.2 の入口②③）は**段階6**。

### 10.1 考え方

| | これまで（第3章） | これから（本章） |
|---|---|---|
| 品質の関門 | 再生リストを1件ずつ承認する | **チャンネルを認定するかどうか**（人が決める唯一の場所） |
| 取り込む範囲 | ハードフィルタを通った再生リストだけ候補にする（外れたものは保存しない） | 認定チャンネルの再生リストは**全件 `playlists` に持つ**。表示・非表示は掲載状態（`listingStatus`）で分ける |
| 掲載 | 承認したものだけ | チャンネルごとに「自動で掲載」か「確認してから掲載」（既定）を選ぶ |
| ゲーム | 承認にゲームタイトル（またはゲーム未設定）が必要 | **ゲームは任意の属性**。分かれば付け、分からなければゲーム未設定（`gameId: null`）のまま掲載する |
| 新着・新しい再生リストの発見 | 週1の探索＋毎日の新着取得（別々） | 毎日のチャンネル巡回に一本化（YouTube定期取得仕様書 第8章） |

- 除外・非ゲームの再生リストも**消さずに持つ**。消すと次の巡回でまた「新しい再生リスト」として判定・確認にかかるため（2026-11-01 ユーザー決定）。
- 格付け（レビュー・ランキング）は今のまま**再生リスト単位**。チャンネル単位では、そのチャンネルの再生リストの評価をまとめて見せるだけで、チャンネル自体の評価は作らない（リブランディング検討 項目2）。

### 10.2 チャンネルの認定

認定チャンネルは `exploration_channels`（Firestore データモデル設計書 §3.32）で管理する。`status: active` が認定済み。

**認定の入口（3つ）**

| 入口 | 内容 | 仕様書 |
|---|---|---|
| ① 運営の直接登録 | 管理画面でチャンネルURL・@ハンドル・名前から登録する（§3.1 と同じ） | 収集候補レビューUI仕様書 §6・§9 |
| ② 実況者本人・事務所の申請 | 「チャンネルを申請する」ページから申請し、運営が審査する | ページ チャンネルを申請する 仕様書／審査ワークフロー仕様書 §15 |
| ③ 視聴者の推薦 | 同じページから「好きなチャンネルを推薦する」として申請し、運営が審査する | 同上 |

**認定の基準**: 実況者本人、または公式（事務所など）のチャンネルであること。切り抜き・転載・まとめチャンネルは認定しない。ゲーム実況が中心かどうかは問わない（ゲーム以外が混ざる分は §10.4 の判定と確認ではじく）。最終判断は運営が行う。

**チャンネルの状態**（`exploration_channels.status`。v4.0 で `opted_out` を追加）

| 状態 | 意味 | 巡回 | そのチャンネルの再生リスト |
|---|---|---|---|
| `unresolved`／`pending_confirm` | チャンネル未特定・確認待ち（§3.1） | しない | — |
| `active` | **認定済み** | する | §10.4 の判定どおり |
| `excluded` | 認定しない・認定を外した（基準に合わない等） | しない | すべて `channel_off`（§10.6） |
| `opted_out` | 実況者・事務所の申し出で掲載を止めた | しない | すべて `channel_off`。申請・提案でも再掲載しない（§10.6） |

**チャンネルごとの設定**

| 設定 | 値 | 既定 | 内容 |
|---|---|---|---|
| 掲載方法（`publishMode`） | `confirm`（確認してから掲載）／`auto`（自動で掲載） | `confirm` | §10.4 の判定で掲載候補になった再生リストを、運営の確認を待って掲載するか、すぐ掲載するか |
| チャンネル単位のタグ（`tagIds`） | 運営者タグ | なし | §3.5 と同じ。掲載するときに固定タグとして付ける |
| 表示順（`featuredOrder`） | 数値（小さいほど先） | なし | 「人気のチャンネル」の仮の並び（ページ top 仕様書 §6A）。人気の決め方が決まるまで運営が手で並べる |

- 「確認するまで出さない（精査 Q1=B）」は、掲載方法の既定値を `confirm` にすることで引き継ぐ。判定の基準が固まった認定チャンネルから `auto` に切り替える。にじさんじのように案件・ゲーム以外の企画が多く混ざるチャンネルは `confirm` のままにする。

### 10.3 取り込み（巡回）

認定チャンネル（`active`）を毎日巡回し、チャンネルの全再生リスト（`playlists.list?channelId`、50件ごとに1ユニット）を取る。手順・クォータ・新着監視との関係は YouTube定期取得仕様書 第8章で定める。

- プレミテに無い再生リストは、`playlists` に**メタ情報だけ**（タイトル・サムネイル・チャンネル・動画数・公開状態・作成日時）で作り、§10.4 の判定で掲載状態を決める。
- 動画一覧（`videos`）は、掲載状態が `listed` になったときに初めて取る（非表示のものはクォータと書き込みを抑えるため取らない）。例外は §10.7。
- 認定した直後（新規の認定・`excluded` からの戻し）は、そのチャンネルの再生リストをその場で1回取り込む（巡回を待たない）。

### 10.4 掲載状態の判定（ルールのみ。AIは使わない）

新しく取り込んだ再生リストは、上から順に判定し、最初に当たったもので掲載状態（`listingStatus`）を決める。

| 順 | 条件 | 掲載状態 | 検索面 | 動画一覧 |
|---|---|---|---|---|
| 1 | タイトルに**除外語**を含む（§10.5） | `excluded`（ゲーム実況だがシリーズとして扱わない） | 出さない | 取らない |
| 2 | タイトルに**非ゲーム語**を含む（§10.5） | `non_game`（ゲーム実況ではない） | 出さない | 取らない |
| 3 | 動画数が10本未満 | `too_short` | 出さない | 取らない。巡回で10本以上になったら1・2を確かめ直してから4へ |
| 4 | チャンネルの掲載方法が `confirm` | `unconfirmed`（確認待ち） | 出さない | 取らない。確認で掲載にしたときに取る |
| 5 | チャンネルの掲載方法が `auto` | `listed`（掲載中） | **出す** | 取る |

- 公開状態が `public` 以外の再生リストは掲載しない（今の `isPublic: false` と同じ扱い）。
- ゲームの推定（§3.4）は判定と同時に行い、当たればゲームを付ける（`gameSetBy: auto`）。当たらなければゲーム未設定（`gameId: null`）で、ゲームらしい語句を `gameHint` に残す（PR #14 段階A・B の「ゲーム未設定」と自動紐づけをそのまま使う）。**ゲームが決まらないことは掲載の妨げにしない**。
- タグ候補（§3.5）は掲載状態が `listed` になったときに付ける。
- 判定の理由（当たった言葉、`too_short` など）を `listingReason` に、決めた者を `listingSetBy`（`auto`／`admin`）に残す。
- **一度決めた掲載状態は、次の巡回で判定し直さない**。例外は (a) `too_short` が10本に達したとき、(b) 管理者が言葉の表を変えて「判定し直す」を押したとき。どちらも `listingSetBy: admin`（人が決めたもの）は上書きしない。
- 「ゲーム未設定（`gameId: null`）」と「ゲームではない（`non_game`）」は別物として持つ。前者はゲーム実況だがどのゲームか分からないもの、後者はそもそもゲーム実況でないもの。

### 10.5 除外語・非ゲーム語

言葉の表は管理画面で追加・削除できるようにする（収集候補レビューUI仕様書 §8.4）。保存先は `app_settings/listing_rules`（データモデル設計書 §3.28）。大文字・小文字と全角・半角は区別しない。初期値は次のとおり（たたき台。ユーザーから一任、2026-11-01）。

| 種類 | 言葉（初期値） |
|---|---|
| 除外語（`excluded`） | 単発／切り抜き／まとめ動画／ダイジェスト／ハイライト／名場面／ショート／Shorts／#shorts／配信アーカイブ／生放送／メンバー限定／告知／お知らせ |
| 非ゲーム語（`non_game`） | 雑談／歌ってみた／歌枠／弾いてみた／踊ってみた／演奏／オリジナル曲／MV／Vlog／ブイログ／料理／食レポ／食べてみた／飲んでみた／旅行／開封／買ってきた／ラジオ／対談／ドッキリ／大喜利／実写／オフ会／筋トレ／ASMR |

- 「アーカイブ」「コラボ」「企画」「検証」「やってみた」「レビュー」はゲーム実況にも付くため、初期値には入れない（確認画面の実績を見て足す）。
- 「まとめ動画」はYouTube側の総集編の意味（プレミテのまとめ機能とは関係ない）。
- 第3章の除外語（§3.3。PR #14 v3.5 で非ゲームの言葉も足した一覧）は、段階4の実装でこの表に移す。

### 10.6 認定を外す・掲載を止める

- **認定を外す**（`active` → `excluded`）: 基準に合わないと分かったとき。そのチャンネルの再生リストをすべて `channel_off`（`listingReason: channel_excluded`）にし、元の掲載状態を `previousListingStatus` に残す。認定し直したら元の状態に戻す。
- **掲載を止める**（`active` → `opted_out`）: 実況者・事務所から「掲載を外してほしい」と申し出があったとき（窓口はお問い合わせ。ページ 実況者・事務所の方へ 仕様書 §4）。**申し出を受けたらすぐ**、そのチャンネルの再生リストをすべて `channel_off`（`listingReason: opt_out`）にする。
  - `opted_out` のチャンネルは、チャンネル申請・再生リスト提案でも再掲載しない（申請画面で受け付けない）。再掲載は本人からの申し出があったときに運営が戻す。
  - 申し出たチャンネルの再生リストを、既にマイリストに入れているユーザーにどう見せるかは §10.7 の表のとおり（**ユーザー確認中**: 既定案は「マイリスト・視聴履歴からも開けなくし、『掲載を終了しました』と出す」）。
- いずれも再生リスト・動画・レビュー・マイリストのデータは消さない（レビューは表示・集計から外れるだけ）。

### 10.7 掲載状態とユーザーの記録

| 掲載状態 | 検索面（再生リストを探す・TOP・ゲーム・チャンネル・タグ・関連） | 再生リスト詳細のURL・マイリスト・視聴履歴から | 新着の監視 |
|---|---|---|---|
| `listed` | 出す | 開ける | する |
| `unconfirmed`／`non_game`／`excluded`／`too_short` | 出さない | 開ける（精査 Q2=A） | マイリスト登録者がいればする（動画一覧も取る） |
| `channel_off`（`channel_excluded`） | 出さない | 開ける | マイリスト登録者がいればする |
| `channel_off`（`opt_out`） | 出さない | §10.6 のユーザー確認中の既定案では**開けない**（「掲載を終了しました」と出す） | しない |

- 「検索面」の絞り込みは「公開（`isPublic`）かつ `listingStatus == 'listed'`」とする（§10.9）。
- 掲載していない再生リストは、ゲーム・チャンネル・ジャンルの件数（`playlistCount` など）にも数えない。

### 10.8 YouTube のデータの保存期間（YouTube API サービス規約）

YouTube API Services Developer Policies（III.E.4）は、ユーザーの認可なしに取った API データ（再生リスト・動画・チャンネルの情報）を**30日を超えて保存するときは、30日以内に取り直すか消す**ことを求めている。また、保存した API データは今の YouTube のデータと合うよう努め、画面にはできるだけ新しいものを出す（III.E.4.e・f）。（2026-11-01 確認。正式な文面は規約の原文で確かめること）

- 認定チャンネルの再生リスト（掲載状態を問わず）は、毎日の巡回でタイトル・サムネイル・動画数を取り直すので満たす。
- 掲載中の再生リストの動画一覧は、動画数が変わらない限り取り直さない（YouTube定期取得仕様書 §7）ため、**30日に1回は全件を取り直す**（YouTube定期取得仕様書 §8.4）。
- `channel_off` の再生リストのうち、ユーザーの記録（マイリスト・レビュー・視聴履歴）が無いものは、30日を過ぎたら `playlists`・`videos` のドキュメントを消す（認定し直せば巡回で作り直される）。記録があるものは、新着の監視（§10.7）で取り直すか、`opt_out` のときは YouTube 由来の項目（タイトル・サムネイル等）を消してプレミテの記録だけ残す。
- 登録者数（`subscriberCount`）などの統計値は30日を超えて持たない（III.E.4.b）。チャンネル更新バッチ（週1）で取り直すか、使わないなら保存しない。

### 10.9 段階3で先に入れること（掲載状態の追加と移行）

段階4（巡回・自動判定）の前に、次を入れる。

1. `playlists` に掲載状態のフィールド（データモデル設計書 §3.2）を足し、既存の再生リストを一回だけのスクリプトで移行する。
   - 既存の再生リストが属するチャンネル（stg では17チャンネル）を一覧で確認し、本人・公式のチャンネルは認定チャンネル（`exploration_channels` に `active` で登録）にする。
   - 認定したチャンネルの再生リストは `listed`（`listingSetBy: admin`）、基準に合わないチャンネル（切り抜き・転載など）の再生リストは `channel_off`（非表示。消さない）にする。
   - マイリスト・レビュー・視聴履歴は壊さない。本番の件数は移行前に数える（友人テスト前で実利用はほぼ無い見込み）。
2. 検索面を「公開かつ `listed`」に絞る（再生リストを探す・TOP・ゲームタイトル詳細・チャンネル・タグ・関連表示・`lib/playlist-aggregates.ts` の集計）。
   - 実装: 一覧の取得（`fetchPublicPlaylists`・`fetchPlaylistsByGame`・`fetchPlaylistsByChannel`）と集計（`lib/playlist-aggregates.ts`）に `listingStatus == 'listed'` を足した。等価条件だけなので複合インデックスは不要。ゲーム・チャンネルの一覧の件数は `playlists` から掲載中だけを数える。チャンネル詳細は、再生リストがすべて `channel_off` のときだけ 404 にする（掲載中が0件で確認待ちがあるチャンネルは空状態で開く）。
   - 実装: `scripts/migrate-listing-status.mjs`（`npm run migrate:listing:stg`／`:prod`）。既定は確認だけで書き込まない。`--off=<YouTubeチャンネルID,…>` で非表示にするチャンネルを指定し、`--apply` で反映する。何度実行しても結果は同じ（`listingStatus` が既にある再生リストは変えない）。
   - 移行で書く値: 掲載は `listed`（`listingReason: migration`）、非表示は `channel_off`（`listingReason: channel_excluded`・`previousListingStatus: listed`）。どちらも `listingSetBy: admin`。`source` は提案者がいれば `user_proposal`、収集候補の承認済みなら `collection_candidate`、それ以外は `admin`。掲載するチャンネルは `exploration_channels` を `active`（`publishMode: confirm`・`authorizedVia: migration`、既にあるものはそのまま）にそろえ、名前が同じ未特定のものは `active` に上げる。非表示にするチャンネルの認定は `excluded` にする。
   - 件数（`games.playlistCount`・`channels.playlistCount`・`tags.usagePlaylistCount`）は掲載中の再生リストだけで数え直す。
   - **本番では、移行を適用してからアプリをデプロイする**（先にデプロイすると、移行前の再生リストが検索面から消える）。
   - 以後の登録（管理者の直接登録・収集候補の承認・提案の承認）は、そのまま `listed`（`listingSetBy: admin`）で作る。ゲームの付け外し（PR #14 段階B）の `games.playlistCount` の増減は、掲載中の再生リストのときだけ行う。
3. 残っている収集候補（`collection_candidates` の未処理）は、段階4で巡回に切り替えるときに一括で §10.4 の判定にかけ、役目を終える（コレクションは消さずに残す）。

### 10.10 クォータ

| 処理 | 消費の目安 |
|---|---|
| 巡回（80チャンネル、1チャンネル約160再生リスト） | 約320 / 日 |
| 掲載になった再生リストの動画一覧・再生時間の取得 | 約 (動画数 ÷ 50) × 2 ＋ 1 / 件 |
| 30日ごとの全件取り直し（§10.8） | 掲載中の再生リストの総ページ数 ÷ 30 / 日（5,300件なら約180 / 日） |
| 初回の一括取り込み（80チャンネル・約5,300件が掲載になる場合） | 約13,000。1日の上限を守って数日に分ける |

1日の上限は第6章と同じく収集用 6,000、新着の監視用 4,000 を目安とし、超えそうなら残りは翌日に回す。新着の監視（既存ユーザーへの通知）を新しい再生リストの取り込みより優先する。
