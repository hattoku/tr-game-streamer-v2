## 1. 概要

> **リブランディング（v4.0、2026-11-01 決定）**: プレミテは「ゲーム起点の再生リスト格付け」から「**掲載チャンネル（実況者本人・公式のチャンネル）の再生リストを、みんなで見て評価するwiki的なサービス**」に考え方を改めた（プレミテ企画書 §0.0）。これに合わせ、収集の品質の関門を「再生リスト1件ずつの承認」から「**チャンネルを掲載するかどうか**」に移す。新しい仕組みは **第10章** で定める。
> - 第10章は段階4（収集の変更、v4.3・2026-11-04）で実装した。**第2章・第3章の「探索 → 収集候補 → まとめて承認」は第10章に置き換わり、今は動いていない**（経緯として残す）。第3章のうち §3.1 のチャンネルの特定・§3.4 のゲーム推定・§3.5 のタグ候補は第10章でもそのまま使う。実装の詳細は §10.11。
> - 「掲載チャンネル」は社内・仕様書上の呼び名で、**お客様から見える画面には出さない**（画面上は「チャンネル」「人気のチャンネル」などと表現する）。
> - 決定の全文: プロジェクトファイル `plans/チャンネル起点運用/リブランディング-検討項目.md`（決定ログ）、精査: 同フォルダ `チャンネル起点運用-精査と方針案.md`。

本仕様書は、プレミテへの登録候補となる再生リストを自動で集める機能の設計を定義する。

v3.0（2026-10-26）で、収集の起点を**有名実況チャンネル**に変更した。友人テストの前に再生リスト・ゲームタイトル・タグを揃えるため、Gemini による品質判定を含まない**最小版**を先に実装する。

| 機能 | 状態（v4.8） | 概要 |
|------|------|------|
| 掲載チャンネルの巡回と掲載状態の判定 | **実装済み（段階4、2026-11-04）** | 掲載チャンネルを毎日巡回し、全再生リストを `playlists` に持ち、ルールで掲載状態を決める。掲載方法（自動で掲載／確認してから掲載）はチャンネルごと（第10章） |
| チャンネル起点の探索と収集候補の承認 | 取り下げ（段階3まで） | 探索対象チャンネルを週1で探索して収集候補に保存し、管理者が承認して登録していた（取り下げ/収集候補による収集（段階3まで）.md） |
| 新作タイトル検知・ゲームタイトル起点の補助収集・Gemini による品質スクリーニング | 未実装の構想 | 構想/コンテンツ収集 これから足すかもしれない収集 構想.md |

掲載するかの判断はチャンネル単位で管理者が行う（掲載チャンネルにするか）。掲載チャンネルの再生リストは、掲載方法が「確認してから掲載」（既定）なら管理者が確認して掲載し、「自動で掲載」ならルールの判定を通ったものをそのまま掲載する（§10.2・§10.4）。

### 1.1 チャンネル起点に変更した理由

- **クォータ**: ゲームタイトル名での検索（`search.list`）は1回100ユニットかかる。チャンネルの再生リスト一覧（`playlists.list` の `channelId` 指定）は50件ごとに1ユニットで済み、数十分の一のコストで済む。
- **量**: 有名実況者のチャンネルには実況シリーズが数十本単位で並んでおり、少ない操作で数を揃えられる。
- **品質**: 実績のある実況者単位で選ぶため、スパムや無関係な動画が混ざりにくい。
- **ゲームタイトルとの関係**: 再生リストのタイトルからゲームを推定し、マスタに無いゲームは承認時にその場で登録する。ゲームタイトルが先に揃っていなくても再生リストを集められ、ゲームタイトルも一緒に増える。

### 1.2 網羅の基準

友人テスト前は「ゲーム実況者 @ ウィキ」（https://w.atwiki.jp/gameplayer/ ）に掲載されている実況者を最低限すべて探索対象にする。掲載名の一覧（2026-10-25 時点で80件）を初期データとし、足りない分は管理者が追加する。wiki の文章は使わず、チャンネルを特定するためだけに使う。

## 2. 全体の流れ

> v4.8 で今の流れに書き直した。段階3までの「探索 → 収集候補 → まとめて承認」の図は「取り下げ/収集候補による収集（段階3まで）.md」第1部へ移した。

```
【掲載チャンネルにする】（人が決める唯一の場所。§10.2）
  ① 管理画面の掲載チャンネル画面で、チャンネルURL・@ハンドル・名前から登録して「登録済み」にする（§3.1）
  ② 一般ユーザーのチャンネル申請を、審査ワークフローで承認する（管理 審査ワークフロー仕様書 §4.4）
  ③ 管理者の再生リスト直接登録で、チャンネルも一緒に掲載する（ページ 提案する 仕様書 §9）
    ↓ 加えた直後に、そのチャンネルだけ1回巡回する（lib/channel-sweep-run.ts）

【毎日の巡回】Cloud Scheduler（毎日）／ダッシュボードの「新着動画の再取得」
  POST /api/admin/refresh-new-videos → lib/new-videos-refresh.ts
    ↓
  掲載チャンネル（active）ごとに playlists.list（channelId 指定、50件/1ユニット）（lib/channel-sweep.ts の sweepChannels）
    ↓
  新しい再生リストは playlists にメタ情報だけで作り、掲載状態をルールで決める（§10.4。除外語・非ゲーム語・本数・掲載方法）
  ゲームの推定（§3.4）が当たればゲームを付け、当たらなければゲーム未設定（gameHint を残す）
    ↓
  掲載方法が「自動で掲載」のチャンネルの掲載候補は、その場で掲載（動画一覧を取り、タグを付け、件数を足す）
    ↓
  新着の監視・30日ルールの取り直しと消し込み（§10.8、YouTube定期取得仕様書 第8章）

【確認して掲載する】管理画面「自動掲載の確認」（収集候補レビューUI仕様書 第8章）
  確認待ち（unconfirmed）を見て、掲載する／ゲームではない／対象外にする（lib/listing-server.ts）
  手動の巡回（全チャンネル／1チャンネル）: POST /api/admin/collection/sweep（lib/channel-sweep-run.ts）

【一般ユーザーが拾う】（審査ワークフローを通る）
  掲載チャンネルの再生リストの提案（掲載していないものの掲載）・ゲーム未設定へのゲームの提案・
  詳細ページからの変更の提案（ゲームではない・ゲームが違う・チャンネルの報告など）
  → 管理 審査ワークフロー仕様書 §4
```

- 件数（`games.playlistCount`・`channels.playlistCount`・`tags.usagePlaylistCount`）を動かす処理はどれも `lib/listing-counts.ts`（計算）と `lib/listing-counts-server.ts`（書き込み）を通す（§10.11、リファクタリング②）。

### 2.1 実行基盤

Cloud Functions 基盤は導入していない。**Cloud Run 上の API Route を Cloud Scheduler から `X-Cron-Secret` 付きで呼ぶ**構成とする。管理画面のボタンからは管理者の ID トークンで同じ API を呼ぶ。定期実行しているのは毎日の `POST /api/admin/refresh-new-videos` だけ（手動の巡回 `POST /api/admin/collection/sweep` も `X-Cron-Secret` を受け付けるが、定期のジョブは無い）。

## 3. チャンネルの特定・ゲームの推定・タグ候補

> v4.8: 段階3までは「チャンネル起点の再生リスト探索」の章だった。今も使うのは §3.1（チャンネルの特定。掲載チャンネル画面で使う）・§3.4（ゲームの推定）・§3.5（タグ候補）。§3.2・§3.3・§3.6 は収集候補のためのもので、取り下げ/へ移した。§3.1 の「探索対象チャンネル」は今の「掲載チャンネル」（`exploration_channels`。DB の名前は変えていない）、「探索」は今の「巡回」と読み替える。

### 3.1 探索対象チャンネル

`exploration_channels` コレクション（Firestore データモデル設計書 §3.32）で管理する。

| 状態（`status`） | 意味 |
|------|------|
| `unresolved` | 名前だけ登録された状態。YouTube のチャンネルは未特定 |
| `pending_confirm` | 名前で検索し、候補（最大5件）が付いた状態。管理者の確認待ち |
| `active` | チャンネルが確定し、探索の対象になっている |
| `excluded` | 管理者が除外した（ゲーム実況中心でない、見つからない等）。探索しない |

- **名前からの特定**: `search.list`（`type=channel`、`maxResults=5`、`regionCode=JP`、`relevanceLanguage=ja`）で候補を取り、`channels.list` で登録者数・アイコンを補う。1件あたり約101ユニットかかるため、管理画面からは**1回あたりの件数上限（既定40件）**を設けて実行する。80件なら2日に分けて実行する。
- **URL・ハンドルからの特定**: `https://www.youtube.com/@handle`・`https://www.youtube.com/channel/UC...`・`@handle`・`UC...` を受け付け、`channels.list`（`forHandle` または `id`）で直接特定する（1ユニット）。名前検索で正しい候補が出なかった場合の手段にもなる。
- **重複**: 同じ YouTube チャンネルIDの `active` が既にある場合は確定できない。
- **チャンネル単位のタグ**: タグマスタのうち運営者タグ（`origin: operator`）から選ぶ。そのチャンネルの再生リストを承認するときに付与する。

### 3.2 探索の実行（取り下げ）

### 3.3 ハードフィルタ（取り下げ）

### 3.4 ゲームの推定

再生リストのタイトルと、登録済みのゲームタイトル（`games.title`）を照合する。

1. 両方を正規化する（Unicode NFKC、小文字化、空白・記号の除去）。
2. 正規化したゲームタイトルが、正規化した再生リストタイトルに含まれるものを候補とする（2文字以下のタイトルは誤一致を避けるため対象外）。
3. 候補が複数ある場合は、最も長く一致したものを採用する。
4. 一致しない場合は「推定なし」とし、ゲーム未設定（`gameId: null`）で取り込む（§10.4）。あわせて、再生リストタイトルからゲーム名らしい部分（`【】`・`［］`・`「」` で囲まれた部分、なければ「実況」「#」「Part」等より前の部分）を抜き出し、再生リストの `gameHint` として保存する（段階3までは収集候補の `gameQuery`）。ゲームが登録・編集されたときに、ゲーム未設定の再生リストと照合して自動で付ける（`lib/playlist-game-linking.ts`）。

### 3.5 タグ候補

掲載するとき（掲載状態が `listed` になったとき）に固定タグとして付けるタグ。**タグマスタの運営者タグ（`origin: operator`）だけを使い、新しいタグは作らない。**

| 由来 | 内容 |
|------|------|
| チャンネル単位 | 掲載チャンネルに設定したタグ（例: 生声・男性実況者・ゆっくり・Vtuber） |
| タイトルの語句 | 再生リストタイトルに含まれる語句から対応するタグを付ける。対応表は `lib/playlist-title-rules.ts` に定数で持つ |

語句とタグの対応（初期値）:

| 語句（いずれかを含む） | タグ |
|------|------|
| 初見 | 初見プレイ |
| 縛り | 縛りプレイ |
| RTA | RTA |
| ノーダメ | ノーダメージ |
| 低レベル | 低レベルクリア |
| 全実績、トロコン、トロフィーコンプ | 全実績解除 |
| やり込み | やり込みプレイ |
| ゆっくり | ゆっくり |
| VOICEROID、ボイロ、ゆかり、琴葉 | VOICEROID |
| ノーカット | ノーカット |
| 字幕 | 字幕・テロップ充実 |
| 協力 | 協力プレイ |
| 対戦 | 対戦メイン |
| 考察 | 考察メイン |
| 攻略 | 攻略メイン |
| 解説 | 解説メイン |
| 二人、2人、三人、3人、4人、複数人、コラボ | 複数人プレイ |

## 6. クォータ管理方針

- YouTube Data API の1日の上限は 10,000 ユニット。**API キーは本番・stg で共有**している（HANDOFF.md 未解決13）ため、stg での試行は少数のチャンネルに絞る。
- 本機能の消費は `collection_quota_logs/{YYYY-MM-DD}`（日本時間の日付）に積算する。既存の動画更新バッチ（`api_quota_logs`）とは分けて記録する。
- **1日の上限（既定 6,000 ユニット）**を超える操作は実行前に拒否する。既存の新着動画取得の分（最大約2,000ユニット/回）を残すため。
- 消費の目安:

| 操作 | 消費 |
|------|------|
| 名前からチャンネルを特定 | 約101ユニット/件（search.list 100 + channels.list 1） |
| URL・ハンドルからチャンネルを特定 | 1ユニット/件 |
| 巡回（1チャンネル） | 再生リスト50件ごとに1ユニット |
| 掲載（1再生リスト） | 約 (動画数 ÷ 50) × 2 + 2 ユニット（掲載時の動画・長さ取得） |

- 毎日の巡回は新着の監視用の枠（1回 4,000）、手動の巡回・掲載の操作は収集の枠（1日 6,000）で数える（§10.10・§10.11）。

| 1チャンネルの再生リストが非常に多い場合 | 数百本の再生リストを持つチャンネルの扱い（現状は全件取得） |
| 収集の操作の権限 | 掲載チャンネル・自動掲載の確認の操作をオーナー限定にするか（現状は管理者＝オーナー・運営者） |

> 新作タイトル検知バッチの検討事項（候補数の上限・機種の絞り込み）は、構想と一緒に「/document/specification/構想/コンテンツ収集 これから足すかもしれない収集 構想.md」へ移した。

## 10. 掲載チャンネルの自動掲載（リブランディング後の収集）

> 実装段階: **段階4**（収集の変更）。掲載状態（`listingStatus`）の追加と既存データの移行・検索面の絞り込みは**段階3**で先に入れる（§10.9）。チャンネル申請（§10.2 の入口②③）は**段階6**。

### 10.1 考え方

| | これまで（第3章） | これから（本章） |
|---|---|---|
| 品質の関門 | 再生リストを1件ずつ承認する | **チャンネルを掲載するかどうか**（人が決める唯一の場所） |
| 取り込む範囲 | ハードフィルタを通った再生リストだけ候補にする（外れたものは保存しない） | 掲載チャンネルの再生リストは**全件 `playlists` に持つ**。表示・非表示は掲載状態（`listingStatus`）で分ける |
| 掲載 | 承認したものだけ | チャンネルごとに「自動で掲載」か「確認してから掲載」（既定）を選ぶ |
| ゲーム | 承認にゲームタイトル（またはゲーム未設定）が必要 | **ゲームは任意の属性**。分かれば付け、分からなければゲーム未設定（`gameId: null`）のまま掲載する |
| 新着・新しい再生リストの発見 | 週1の探索＋毎日の新着取得（別々） | 毎日のチャンネル巡回に一本化（YouTube定期取得仕様書 第8章） |

- 除外・非ゲームの再生リストも**消さずに持つ**。消すと次の巡回でまた「新しい再生リスト」として判定・確認にかかるため（2026-11-01 ユーザー決定）。
- 格付け（レビュー・ランキング）は今のまま**再生リスト単位**。チャンネル単位では、そのチャンネルの再生リストの評価をまとめて見せるだけで、チャンネル自体の評価は作らない（リブランディング検討 項目2）。

### 10.2 チャンネルの掲載

掲載チャンネルは `exploration_channels`（Firestore データモデル設計書 §3.32）で管理する。`status: active` が登録済み。

**掲載の入口（3つ）**

| 入口 | 内容 | 仕様書 |
|---|---|---|
| ① 運営の直接登録 | 管理画面でチャンネルURL・@ハンドル・名前から登録する（§3.1 と同じ） | 収集候補レビューUI仕様書 §6・§9 |
| ② チャンネル申請（実況者本人・事務所・視聴者の推薦を区別しない。2026-11-16 以降） | 「提案する」（`/propose`）のチャンネル側から申請し、運営が審査する | ページ 提案する 仕様書 §6／審査ワークフロー仕様書 §4.4 |
| ③ 管理者の直接登録でのチャンネル同時掲載 | 管理者が掲載していないチャンネルの再生リストを登録するとき、チャンネルも掲載チャンネルにする | ページ 提案する 仕様書 §9 |

**掲載の基準**: 実況者本人、または公式（事務所など）のチャンネルであること。切り抜き・転載・まとめチャンネルは掲載しない。ゲーム実況が中心かどうかは問わない（ゲーム以外が混ざる分は §10.4 の判定と確認ではじく）。最終判断は運営が行う。

**チャンネルの状態**（`exploration_channels.status`。v4.0 で `opted_out` を追加）

| 状態 | 意味 | 巡回 | そのチャンネルの再生リスト |
|---|---|---|---|
| `unresolved`／`pending_confirm` | チャンネル未特定・確認待ち（§3.1） | しない | — |
| `active` | **登録済み** | する | §10.4 の判定どおり |
| `excluded` | 掲載しない・掲載から外した（基準に合わない等） | しない | すべて `channel_off`（§10.6） |
| `opted_out` | 実況者・事務所の申し出で掲載を止めた | しない | すべて `channel_off`。申請・提案でも再掲載しない（§10.6） |

**チャンネルごとの設定**

| 設定 | 値 | 既定 | 内容 |
|---|---|---|---|
| 掲載方法（`publishMode`） | `confirm`（確認してから掲載）／`auto`（自動で掲載） | `confirm` | §10.4 の判定で掲載候補になった再生リストを、運営の確認を待って掲載するか、すぐ掲載するか |
| チャンネル単位のタグ（`tagIds`） | 運営者タグ | なし | §3.5 と同じ。掲載するときに固定タグとして付ける |
| 表示順（`featuredOrder`） | 数値（小さいほど先） | なし | 「人気のチャンネル」の仮の並び（ページ top 仕様書 §6A）。人気の決め方が決まるまで運営が手で並べる |

- 「確認するまで出さない（精査 Q1=B）」は、掲載方法の既定値を `confirm` にすることで引き継ぐ。判定の基準が固まった掲載チャンネルから `auto` に切り替える。にじさんじのように案件・ゲーム以外の企画が多く混ざるチャンネルは `confirm` のままにする。

### 10.3 取り込み（巡回）

掲載チャンネル（`active`）を毎日巡回し、チャンネルの全再生リスト（`playlists.list?channelId`、50件ごとに1ユニット）を取る。手順・クォータ・新着監視との関係は YouTube定期取得仕様書 第8章で定める。

- プレミテに無い再生リストは、`playlists` に**メタ情報だけ**（タイトル・サムネイル・チャンネル・動画数・公開状態・作成日時）で作り、§10.4 の判定で掲載状態を決める。
- 動画一覧（`videos`）は、掲載状態が `listed` になったときに初めて取る（非表示のものはクォータと書き込みを抑えるため取らない）。例外は §10.7。
- 掲載した直後（新規の掲載・`excluded` からの戻し）は、そのチャンネルの再生リストをその場で1回取り込む（巡回を待たない）。

### 10.4 掲載状態の判定（ルールのみ。AIは使わない）

新しく取り込んだ再生リストは、上から順に判定し、最初に当たったもので掲載状態（`listingStatus`）を決める。

| 順 | 条件 | 掲載状態 | 検索面 | 動画一覧 |
|---|---|---|---|---|
| 1 | タイトルに**除外語**を含む（§10.5） | `excluded`（ゲーム実況だがシリーズとして扱わない） | 出さない | 取らない |
| 2 | タイトルに**非ゲーム語**を含む（§10.5） | `non_game`（ゲーム実況ではない） | 出さない | 取らない |
| 3 | 動画数が10本未満 | `too_short` | 出さない | 取らない。巡回で10本以上になったら1・2を確かめ直してから4へ |
| 4 | チャンネルの掲載方法が `confirm` | `unconfirmed`（確認待ち） | 出さない | 取らない。確認で掲載にしたときに取る |
| 5 | チャンネルの掲載方法が `auto` | `listed`（掲載中） | **出す** | 取る |

- 公開状態が `public` 以外の再生リストは掲載しない（今の `isPublic: false` と同じ扱い）。
- ゲームの推定（§3.4）は判定と同時に行い、当たればゲームを付ける（`gameSetBy: auto`）。当たらなければゲーム未設定（`gameId: null`）で、ゲームらしい語句を `gameHint` に残す（PR #14 段階A・B の「ゲーム未設定」と自動紐づけをそのまま使う）。**ゲームが決まらないことは掲載の妨げにしない**。
- タグ候補（§3.5）は掲載状態が `listed` になったときに付ける。
- 判定の理由（当たった言葉、`too_short` など）を `listingReason` に、決めた者を `listingSetBy`（`auto`／`admin`）に残す。
- **一度決めた掲載状態は、次の巡回で判定し直さない**。例外は (a) `too_short` が10本に達したとき、(b) 管理者が言葉の表を変えて「判定し直す」を押したとき。どちらも `listingSetBy: admin`（人が決めたもの）は上書きしない。
- 「ゲーム未設定（`gameId: null`）」と「ゲームではない（`non_game`）」は別物として持つ。前者はゲーム実況だがどのゲームか分からないもの、後者はそもそもゲーム実況でないもの。

### 10.5 除外語・非ゲーム語

言葉の表は管理画面で追加・削除できるようにする（収集候補レビューUI仕様書 §8.4）。保存先は `app_settings/listing_rules`（データモデル設計書 §3.28）。大文字・小文字と全角・半角は区別しない。初期値は次のとおり（たたき台。ユーザーから一任、2026-11-01）。

| 種類 | 言葉（初期値） |
|---|---|
| 除外語（`excluded`） | 単発／切り抜き／まとめ動画／ダイジェスト／ハイライト／名場面／ショート／Shorts／#shorts／配信アーカイブ／生放送／メンバー限定／告知／お知らせ |
| 非ゲーム語（`non_game`） | 雑談／歌ってみた／歌枠／弾いてみた／踊ってみた／演奏／オリジナル曲／MV／Vlog／ブイログ／料理／食レポ／食べてみた／飲んでみた／旅行／開封／買ってきた／ラジオ／対談／ドッキリ／大喜利／実写／くだらない／オフ会／筋トレ／ASMR |

- 「アーカイブ」「コラボ」「企画」「検証」「やってみた」「レビュー」はゲーム実況にも付くため、初期値には入れない（確認画面の実績を見て足す）。
- 「まとめ動画」はYouTube側の総集編の意味（プレミテのまとめ機能とは関係ない）。
- 第3章の除外語（§3.3。PR #14 v3.5 で非ゲームの言葉も足した一覧）は、段階4の実装でこの表に移した（第3章にだけあった「くだらない」は非ゲーム語に入れた）。
- `app_settings/listing_rules` が無いときは、この初期値で判定する（`lib/listing-rules.ts` の `DEFAULT_LISTING_RULES`）。

### 10.6 掲載から外す・掲載を止める

- **掲載から外す**（`active` → `excluded`）: 基準に合わないと分かったとき。そのチャンネルの再生リストをすべて `channel_off`（`listingReason: channel_excluded`）にし、元の掲載状態を `previousListingStatus` に残す。掲載し直したら元の状態に戻す。
- **掲載を止める**（`active` → `opted_out`）: 実況者・事務所から「掲載を外してほしい」と申し出があったとき（窓口はお問い合わせ。ページ 実況者・事務所の方へ 仕様書 §4）。**申し出を受けたらすぐ**、そのチャンネルの再生リストをすべて `channel_off`（`listingReason: opt_out`）にする。
  - `opted_out` のチャンネルは、チャンネル申請・再生リスト提案でも再掲載しない（申請画面で受け付けない）。再掲載は本人からの申し出があったときに運営が戻す。
  - 申し出たチャンネルの再生リストを、既にマイリストに入れているユーザーにどう見せるかは §10.7 の表のとおり（**ユーザー確認中**: 既定案は「マイリスト・視聴履歴からも開けなくし、『掲載を終了しました』と出す」）。
- いずれも再生リスト・動画・レビュー・マイリストのデータは消さない（レビューは表示・集計から外れるだけ）。

### 10.7 掲載状態とユーザーの記録

| 掲載状態 | 検索面（再生リストを探す・TOP・ゲーム・チャンネル・タグ・関連） | 再生リスト詳細のURL・マイリスト・視聴履歴から | 新着の監視 |
|---|---|---|---|
| `listed` | 出す | 開ける | する |
| `unconfirmed`／`non_game`／`excluded`／`too_short` | 出さない | 開ける（精査 Q2=A） | マイリスト登録者がいればする（動画一覧も取る） |
| `channel_off`（`channel_excluded`） | 出さない | 開ける | マイリスト登録者がいればする |
| `channel_off`（`opt_out`） | 出さない | §10.6 のユーザー確認中の既定案では**開けない**（「掲載を終了しました」と出す） | しない |

- 「検索面」の絞り込みは「公開（`isPublic`）かつ `listingStatus == 'listed'`」とする（§10.9）。
- 掲載していない再生リストは、ゲーム・チャンネル・ジャンルの件数（`playlistCount` など）にも数えない。

### 10.8 YouTube のデータの保存期間（YouTube API サービス規約）

YouTube API Services Developer Policies（III.E.4）は、ユーザーの認可なしに取った API データ（再生リスト・動画・チャンネルの情報）を**30日を超えて保存するときは、30日以内に取り直すか消す**ことを求めている。また、保存した API データは今の YouTube のデータと合うよう努め、画面にはできるだけ新しいものを出す（III.E.4.e・f）。（2026-11-01 確認。正式な文面は規約の原文で確かめること）

- 掲載チャンネルの再生リスト（掲載状態を問わず）は、毎日の巡回でタイトル・サムネイル・動画数を取り直すので満たす。
- チャンネル名・アイコン（`channels`・`exploration_channels`・`playlists` の `channelName`・`channelIconUrl`）は、毎日の再取得の最初に YouTube の今の値に合わせる（YouTube定期取得仕様書 §4.4。v4.6）。`opt_out` で YouTube 由来の項目を消した再生リスト（`youtubeDataRemovedAt` があるもの）は対象にしない。
- 掲載中の再生リストの動画一覧は、動画数が変わらない限り取り直さない（YouTube定期取得仕様書 §7）ため、**30日に1回は全件を取り直す**（YouTube定期取得仕様書 §8.4）。
- `channel_off` の再生リストのうち、ユーザーの記録（マイリスト・レビュー・視聴履歴）が無いものは、30日を過ぎたら `playlists`・`videos` のドキュメントを消す（掲載し直せば巡回で作り直される）。記録があるものは、新着の監視（§10.7）で取り直すか、`opt_out` のときは YouTube 由来の項目（タイトル・サムネイル等）を消してプレミテの記録だけ残す。
- 登録者数（`subscriberCount`）などの統計値は30日を超えて持たない（III.E.4.b）。使わないなら保存しない（掲載チャンネルの登録者数は巡回のたびに消す）。

### 10.9 段階3で先に入れること（掲載状態の追加と移行）

段階4（巡回・自動判定）の前に、次を入れる。

1. `playlists` に掲載状態のフィールド（データモデル設計書 §3.2）を足し、既存の再生リストを一回だけのスクリプトで移行する。
   - 既存の再生リストが属するチャンネル（stg では17チャンネル）を一覧で確認し、本人・公式のチャンネルは掲載チャンネル（`exploration_channels` に `active` で登録）にする。
   - 掲載したチャンネルの再生リストは `listed`（`listingSetBy: admin`）、基準に合わないチャンネル（切り抜き・転載など）の再生リストは `channel_off`（非表示。消さない）にする。
   - マイリスト・レビュー・視聴履歴は壊さない。本番の件数は移行前に数える（友人テスト前で実利用はほぼ無い見込み）。
2. 検索面を「公開かつ `listed`」に絞る（再生リストを探す・TOP・ゲームタイトル詳細・チャンネル・タグ・関連表示・`lib/playlist-aggregates.ts` の集計）。
   - 実装: 一覧の取得（`fetchPublicPlaylists`・`fetchPlaylistsByGame`・`fetchPlaylistsByChannel`）と集計（`lib/playlist-aggregates.ts`）に `listingStatus == 'listed'` を足した。等価条件だけなので複合インデックスは不要。ゲーム・チャンネルの一覧の件数は `playlists` から掲載中だけを数える。チャンネル詳細は、再生リストがすべて `channel_off` のときだけ 404 にする（掲載中が0件で確認待ちがあるチャンネルは空状態で開く）。
   - 実装: `scripts/migrate-listing-status.mjs`（`npm run migrate:listing:stg`／`:prod`）。既定は確認だけで書き込まない。`--off=<YouTubeチャンネルID,…>` で非表示にするチャンネルを指定し、`--apply` で反映する。何度実行しても結果は同じ（`listingStatus` が既にある再生リストは変えない）。
   - 移行で書く値: 掲載は `listed`（`listingReason: migration`）、非表示は `channel_off`（`listingReason: channel_excluded`・`previousListingStatus: listed`）。どちらも `listingSetBy: admin`。`source` は提案者がいれば `user_proposal`、収集候補の承認済みなら `collection_candidate`、それ以外は `admin`。掲載するチャンネルは `exploration_channels` を `active`（`publishMode: confirm`・`authorizedVia: migration`、既にあるものはそのまま）にそろえ、名前が同じ未特定のものは `active` に上げる。非表示にするチャンネルで既に `active` のものは `excluded` にする。
   - 件数（`games.playlistCount`・`channels.playlistCount`・`tags.usagePlaylistCount`）は掲載中の再生リストだけで数え直す。
   - **本番では、移行を適用してからアプリをデプロイする**（先にデプロイすると、移行前の再生リストが検索面から消える）。
   - 以後の登録（管理者の直接登録・収集候補の承認・提案の承認）は、そのまま `listed`（`listingSetBy: admin`）で作る。ゲームの付け外し（PR #14 段階B）の `games.playlistCount` の増減は、掲載中の再生リストのときだけ行う。
3. 残っている収集候補（`collection_candidates` の未処理）は、段階4で巡回に切り替えるときに一括で §10.4 の判定にかけ、役目を終える（コレクションは消さずに残す）。

### 10.10 クォータ

| 処理 | 消費の目安 |
|---|---|
| 巡回（80チャンネル、1チャンネル約160再生リスト） | 約320 / 日 |
| 掲載になった再生リストの動画一覧・再生時間の取得 | 約 (動画数 ÷ 50) × 2 ＋ 1 / 件 |
| 30日ごとの全件取り直し（§10.8） | 掲載中の再生リストの総ページ数 ÷ 30 / 日（5,300件なら約180 / 日） |
| 初回の一括取り込み（80チャンネル・約5,300件が掲載になる場合） | 約13,000。1日の上限を守って数日に分ける |

1日の上限は第6章と同じく収集用 6,000、新着の監視用 4,000 を目安とし、超えそうなら残りは翌日に回す。新着の監視（既存ユーザーへの通知）を新しい再生リストの取り込みより優先する。

#### 巡回で作る再生リスト（メタ情報だけ）

| フィールド | 値 |
|---|---|
| `title`・`thumbnailUrl`・`channelId`・`channelName`・`channelIconUrl` | `playlists.list` の値（チャンネル名・アイコンは掲載チャンネルの確定時の値。アイコンの補い方は下記） |
| `videoCount` | YouTube の動画数（`contentDetails.itemCount`）。動画一覧を取るまでは巡回のたびに更新する |
| `youtubeItemCount`・`latestVideoPublishedAt`・`lastFetchedAt`・`fullRefetchedAt` | null（**`youtubeItemCount` が null ＝ まだ動画一覧を取っていない**） |
| `registeredAt`・`registeredBy` | 取り込んだ日時・`"system"` |
| `playlistPublishedAt` | 再生リストの作成日時（`snippet.publishedAt`。v2.5 で追加） |
| `metaFetchedAt` | YouTube のメタ情報を最後に取り直した日時（v2.5 で追加。30日ルールの確認に使う） |
| `gameId` ほか | §10.4 のゲームの推定。当たれば `gameSetBy: auto`、当たらなければ `gameHint` に §3.4 のゲーム名らしい部分 |
| 掲載状態 | §10.4 の判定（`listingSetBy: auto`）。`source: channel_sweep`、`explorationChannelId` |

#### 掲載状態の理由（`listingReason`）

| 値 | 意味 |
|---|---|
| `word:<言葉>` | 除外語・非ゲーム語に当たった（`excluded`／`non_game`） |
| `too_short` | 動画数が最小本数未満 |
| `confirm` | 掲載方法が「確認してから掲載」のチャンネルで、ルールに当たらなかった（`unconfirmed`） |
| `auto_pending` | 掲載方法が「自動で掲載」のチャンネルで、ルールに当たらなかったが、まだ動画一覧を取っていない（`unconfirmed`）。次の手順で掲載する |
| `auto` | 自動で掲載した（`listed`） |
| `admin`／`migration`／`candidate_rejected` | 管理者が決めた／段階3の移行／収集候補で却下済み |
| `channel_excluded`／`opt_out` | チャンネルを掲載から外した／掲載を止めた（`channel_off`） |

- 「自動で掲載」は、動画一覧を取り終えてから `listed` にする（動画の無い再生リストを検索面に出さないため）。判定で `listed` になるものは、いったん `unconfirmed`（`auto_pending`）で作り、同じ巡回の最後に（クォータが足りる分だけ）動画一覧を取って `listed`（`auto`）にする。足りなかった分は翌日に回す。確認画面では「自動で掲載する予定」と出し、手で掲載することもできる。
- 掲載方法を「自動」から「確認」に戻したチャンネルの `auto_pending` は、次の巡回で `confirm` に変える（自動では掲載しない）。「確認」から「自動」に変えても、今ある `confirm` は自動では掲載しない（収集候補レビューUI仕様書 §9.2）。

#### 掲載する・外す（`lib/listing-server.ts`）

- **掲載する**: 動画一覧がまだなら取る（登録と同じ。動画・再生時間を保存し、`youtubeItemCount`・`fullRefetchedAt`・`lastFetchedAt`・`latestVideoPublishedAt` を書く）。タグ（チャンネル単位タグ＋タイトル由来のタグ。画面で外したものを除く）を固定タグとして足し、`games.playlistCount`・`channels.playlistCount`（チャンネルのドキュメントが無ければ作る）・`tags.usagePlaylistCount` を足す。YouTube で見つからなければ失敗として返し、状態は変えない。`channel_off` の再生リストはこの操作では掲載できない（チャンネルの操作で戻す）。
- **ゲームではない／対象外にする／10本未満に戻す／確認待ちに戻す**: 掲載中だったら件数を戻す。動画・タグ・レビュー・マイリストは消さない。
- 件数は「変わる前に数えていた分を引き、変わった後に数える分を足す」で求める（`lib/listing-counts.ts` の `playlistCountDeltas`）。消されたゲーム・タグは飛ばす。
- 状態の切り替えと件数の増減は1件ずつトランザクションで行い、同時に操作しても二重に数えない。

#### 30日ルールの実装（§10.8）

- **監視の対象**（動画一覧を取り直し、新着を通知する）は、公開中（`isPublic`）で、`listed`、または `opt_out` 以外で「マイリスト登録者がいる」か「動画一覧を取ったことがある（`youtubeItemCount` が null でない）かつ `channel_off` でない」もの（`non_game`・`excluded` などに切り替えた動画取得済みのもの）。YouTube定期取得仕様書 §8.2 の「マイリスト登録者がいるときだけ」より広げた。取った動画を古いまま残さないため。`channel_off`（`opt_out` 以外）でマイリスト登録者のいないものは対象にせず、ユーザーの記録（視聴履歴・レビュー・視聴位置）があるときは25日を過ぎる前にメタ情報だけ取り直す（下の消し込み）。
- メタ情報（タイトル・サムネイル）は、掲載チャンネルの再生リストなら巡回で、それ以外の監視の対象なら動画数の確認（`playlists.list` の `id` 指定。`part=snippet,contentDetails,status` で消費は同じ）で毎日取り直し、`metaFetchedAt` を書く。
- 監視の対象の動画一覧は、`fullRefetchedAt`（無ければ `lastFetchedAt`→`registeredAt`）から25日を過ぎたら全件を取り直す（動画のタイトル・サムネイル・順番・再生時間を上書き。再生リストから消えた動画・削除や非公開の動画のドキュメントは消す。YouTube定期取得仕様書 v1.10 §7.2）。1日に回す件数は対象全体の1/25まで（少なくとも10件）にし、古い順に回す。
- **消し込み**: 掲載中でなく、監視の対象でもない再生リストのうち、メタ情報を30日取り直していない（`metaFetchedAt`、無ければ `lastFetchedAt`→`registeredAt` が30日より前）もので、ユーザーの記録（マイリスト・レビュー・視聴履歴・視聴位置）が無いものは、`playlists` と `videos` を消す（チャンネルを掲載し直せば巡回で作り直される）。`opt_out` で記録があるものは、YouTube 由来の項目（タイトル→「掲載を終了した再生リスト」・サムネイル・チャンネル名・アイコン）を空にし、動画のドキュメントを消して、`youtubeDataRemovedAt` を書く。
- 収集候補（`collection_candidates`。もう作られない）の残りは、`collectedAt` から30日を過ぎたら消す。本番で残りが無くなったのを確かめたら、この処理も外してよい（v4.7）。
- 掲載チャンネルの登録者数（`exploration_channels.subscriberCount`）は巡回のたびに null にする（確定のときの確認にだけ使う）。名前検索の候補（`searchCandidates`）の登録者数は、`updatedAt` から30日を過ぎたら null にする。
- 消し込みは1回あたり500件まで（多いときは翌日に続ける）。
