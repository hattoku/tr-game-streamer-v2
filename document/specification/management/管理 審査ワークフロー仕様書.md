## 1. 概要

一般ユーザーからの提案・通報（`workflows` コレクション）を、管理者（オーナー・運営者）が1件ずつ確かめて承認または却下する機能。提出されたワークフローは処理済みになっても消さず、審査の記録として残す（§3.6）。

### 1.1 考え方（2026-11-01 リブランディング以降）

- **運営が入れる再生リストは1件ずつ審査しない**。品質の関門は「チャンネルを掲載するかどうか」で、掲載チャンネルの再生リストは巡回で取り込み、掲載状態のルールと「自動掲載の確認」画面（収集候補レビューUI仕様書 §8）で振り分ける。これは審査ワークフローの外で行う（ワークフローは作らない）。
- 審査ワークフローに来るのは、一般ユーザーが出した次のものだけ（§4）。
  1. **チャンネル申請**: 掲載していないチャンネルを載せてほしい（実況者本人・事務所、視聴者の推薦を区別しない）。
  2. **掲載チャンネルへの再生リスト提案**: 掲載チャンネルの再生リストのうち、自動で拾えなかったもの・掲載していないもの。
  3. **ゲーム未設定の再生リストへのゲームの提案**。
  4. **変更の提案**: 詳細ページの「情報の更新を提案する」（ゲーム・チャンネル・再生リスト）。
  5. **レビューコメントの通報**。
- 掲載していないチャンネルの再生リストの提案は受けない。提案画面でチャンネル申請へ案内する（ページ 提案する 仕様書 §7）。

### 1.2 審査は1段

承認・却下は管理者1人が1回で決める。新しいワークフローは `status: reviewing_lv1`（審査中）で作り、承認すると `approved`、却下すると `rejected` になる。オーナーと運営者の権限は分けない（§2）。

## 2. アクセス権限

| 操作 | オーナー | 運営者 |
|------|:---:|:---:|
| ワークフロー一覧・詳細の閲覧 | ○ | ○ |
| 承認・却下 | ○ | ○ |
| 運営メモの編集 | ○ | ○ |

- 画面は管理画面（`/admin/*`）の中にあり、API はすべて `lib/api-auth.ts` の `requireAdmin` で管理者かを確かめる（オーナー・運営者を区別しない）。
- `workflows` は Firestore のルールで管理者だけが読める。本人が直接読めるのは自分の通報（`review_report`、通報の重複チェック用）だけで、提案者には提案履歴の API（`GET /api/playlists/proposals`。表示用の項目だけ）で返す。運営メモ・内部メモ（`step2History.comment`）は提案者に見せない。

## 3. 状態と共通の操作

### 3.1 状態

| `status` | 画面の表示 | 意味 |
|---|---|---|
| `reviewing_lv1` | 審査中 | 提出されて、まだ承認・却下していない（一覧・詳細のラベルの色は共通 デザイントークン仕様書 §5.4: 審査中＝アンバー／承認＝緑／却下＝赤） |
| `reviewing_lv2` | 審査中 | 二段階の審査のための値。今は作られない（読むときは審査中として扱う） |
| `approved` | 承認 | 承認し、種別ごとの処理（§4）が終わった |
| `rejected` | 却下 | 却下した |

- 承認・却下できるのは審査中のものだけ。処理済みのものに承認・却下を送ると 409 `already_processed`。

### 3.2 承認・却下の操作

```
詳細画面の「承認する」／「却下する」
    ↓
確認ダイアログ
  ├─ 承認: コメント（任意）
  └─ 却下: 種別ごとに、定型の見送り理由（必須・提案者に見せる）＋内部メモ（任意・見せない）
           または自由記述の却下理由（必須・内部メモ）
    ↓
PATCH /api/admin/workflows/[workflowId]（action: approve / reject）
    ↓
種別ごとの処理（§4）→ 状態の確定・提案者への通知（§3.4）
    ↓
詳細画面はワークフローを購読しているので、そのまま結果が出る
```

| 種別 | 却下に要るもの |
|---|---|
| 再生リスト登録提案・チャンネル申請・変更の提案 | 定型の見送り理由（`rejectReasonCode`）。自由記述は任意の内部メモ |
| レビューコメント通報・ゲームタイトル登録提案 | 自由記述の却下理由（必須。内部メモ） |

- 承認・却下の記録は `step2History` に1件足す（`executedAt`・`operatorId`・`isAI: false`・`action: approved / rejected`・`comment`。変更の提案は `approveAction`・`gameId`・`gameName` も）。二段階の審査は作っていないため、`step1History` は使わない。
- 承認できなかったとき（YouTube で見つからない、掲載チャンネルから外れた、など）は、エラーを画面に出して審査中のまま残す。エラーコードと文言は種別ごと（§4）。

### 3.3 同時に操作したとき

- 時間のかかる承認（再生リストの登録・掲載、チャンネルを掲載チャンネルに加える、変更の提案の処理）の前に、承認処理中の印（`workflows.approvingAt`）をトランザクションで立てる。有効な印があれば 409 `already_processed`。印は2分で失効し、処理が途中で落ちても詰まらない。承認できなかったときは印を外す。
- 状態の確定（`status`・`step2History`・種別ごとの項目）と提案者への通知は、1つのトランザクションで1回だけ書く。書く前に、まだ審査中であることと、却下なら承認処理中の印が有効でないことを確かめる（並行した承認・却下で状態と通知が食い違わないように）。

### 3.4 審査結果の通知

承認・却下のとき、提案した人にサイト内通知（`notifications`、`type: "review_result"`。ページ ユーザー通知機能仕様書 §2.1）を作る。

| 種別 | 承認 | 却下 |
|---|---|---|
| 再生リスト登録提案 | 再生リスト「{タイトル}」の提案が承認され、公開されました（遷移先は再生リスト詳細） | 再生リスト「{タイトル}」の提案は見送りになりました（{定型の理由}）（遷移先は提案履歴） |
| ゲームタイトル登録提案（再生リストに付けたいもの） | ゲームタイトル「{名前}」の提案が承認され、再生リストに登録されました | ゲームタイトル「{名前}」の提案は見送りになりました（運営の判断で、既存のゲームタイトルに合わせるか、登録を見送りました） |
| チャンネル申請 | チャンネル「{名前}」の申請が承認されました。再生リストは運営の確認のあと順に公開します | チャンネル「{名前}」の申請は見送りになりました（{定型の理由}） |
| 変更の提案 | {ゲーム／チャンネル／再生リスト}「{名前}」への提案を反映しました。ありがとうございます（報告した全員） | {…}「{名前}」への提案は見送りになりました（{定型の理由}）（報告した全員） |
| レビューコメント通報・旧形式のゲームタイトル登録提案 | 通知しない | 通知しない |

### 3.5 運営メモ

ワークフローごとに管理者の内部メモ（`operatorMemo`）を書ける。提案者には見せない。

| 項目 | 仕様 |
|------|------|
| 編集 | 詳細画面の「編集する」→「保存する」（`PATCH`、`action: update_memo`）。審査中・処理済みのどちらでも書ける |
| 文字数 | 1,000文字まで（超えた分は切る）。空にすると消える |

### 3.6 削除ポリシー

ワークフローは物理削除しない。承認・却下したものも審査の記録として残す。

## 4. 種別ごとの審査

| 種別（`workflows.type`） | 一覧のセクション | 入口（起票） | 承認したときの処理 | 処理のファイル |
|---|---|---|---|---|
| レビューコメント通報 `review_report` | 通報 | レビュー一覧の「通報する」（クライアントから直接作る） | 対象のレビューを論理削除（非表示） | `lib/review-report-server.ts` |
| 再生リスト登録提案 `playlist_register` | 提案 | 提案する（`/propose`）の再生リスト側（`POST /api/playlists/propose`） | 再生リストを登録・掲載する | `lib/playlist-proposal-server.ts` |
| ゲームタイトル登録提案 `game_title_register` | 提案 | 再生リスト詳細の「ゲームを登録」（`POST /api/playlists/[playlistId]/game-proposal`） | 再生リストにゲームを付ける | `lib/game-proposal-server.ts` |
| チャンネル申請 `channel_application` | 提案 | 提案する（`/propose`）のチャンネル側（`POST /api/channels/apply`） | 掲載チャンネルに加え、再生リストを1回取り込む | `lib/channel-application-server.ts` |
| 変更の提案 `game_title_edit`・`channel_report`・`playlist_report` | 通報 | 詳細ページの「⋯」→「情報の更新を提案する」（`POST /api/change-proposals`） | 理由ごとの処理（同じ対象の提案をまとめて） | `lib/change-proposal-server.ts` |

- 一覧（§5.1）の「通報」「提案」のどちらに並べるかも上の表のとおり。

### 4.1 レビューコメント通報（`review_report`）

| 項目 | 仕様 |
|---|---|
| 記録 | `reportData`: `reviewId`・`playlistId`・`reason`（スパム・荒らし・不適切・その他）・`detail` |
| 詳細 | 通報理由・補足、対象のレビュー（投稿者・星・コメント。今の内容を購読し、非表示になれば「非表示」）、再生リストのタイトル |
| 承認 | 対象レビューを**論理削除**する（下表）。却下は掲載継続 |
| 却下 | 自由記述の理由が必須（内部メモ）。通報した人には通知しない |

承認したときの論理削除（2026-10-24 ユーザー決定。誹謗中傷等は「削除」ではなく「無効化」で扱い、将来の改ざん不可能性の担保に向けて reviewId は消さない）:

|項目|仕様|
|---|---|
|対象レビュー|`reviews` ドキュメントは削除せず、`isHidden: true`・`hiddenAt`・`hiddenByWorkflowId` を記録する。星評価・コメント等の内容はそのまま保持する。読み取りから非表示化までをトランザクションにし、その間に本人が削除・更新しても取りこぼさない|
|審査記録への退避|承認時点のレビュー内容（投稿者・星評価・コメント・ネタバレフラグ・投稿日時）を `workflows.reportData.hiddenReviewSnapshot` に保存する。投稿者が後でレビューを削除しても、非表示にした内容は審査履歴として残る|
|表示・集計からの除外|非表示のレビューは、レビュー一覧（他ユーザー向け）・集計サマリー・再生リストスコアと `playlists.reviewCount`・プロフィールのレビュー履歴と統計（本人が見る場合も含む）・`users.reviewCount` から除外する（承認のときに `users.reviewCount` を1減らし、再生リストのスコアを計算し直す）。「参考になった」の新規押下も不可|
|投稿者本人|自分のレビューカードには「非表示」バッジと案内を表示する。編集しても非表示のまま。星評価とコメントが両方なくなる（「レビューを削除する」、星評価の取り消しとコメントの削除、視聴ステータスも含めてすべて外す、のいずれか）と非表示が解け、新しく書き直せる（非表示にした内容は審査記録に残っているため）|
|既知の制約|非表示のレビューもセキュリティルール上は読み取り可能で、表示側で除外している。一般公開（フェーズ8）までに、ルールで本人・管理者以外の読み取りを禁じる対応を検討する|
|視聴記録への影響|なし。視聴ステータスの正は `mylist` 側のため、マイリスト・視聴履歴はそのまま使える|

### 4.2 再生リスト登録提案（`playlist_register`）

入口と受け付けのルールは「ページ 提案する 仕様書」§5。

| 項目 | 仕様 |
|---|---|
| 提案できる再生リスト | 掲載チャンネル（`exploration_channels.status: active`）の再生リストだけ。掲載チャンネルかは提案時と承認時の両方で確かめる |
| 記録 | `proposalData`: 再生リスト（`playlistUrl`・`youtubePlaylistId`・`title`・`channelId` など）、ゲーム（`gameId`・`gameName`。新しいゲームの名前は `newGameTitle`・`newGameNote`・`newGamePlatforms`・`newGameRakuten`。ゲームが分からないときは `noGame: true`）、すでにプレミテにある掲載していない再生リストなら提案時点の掲載状態 `existingListingStatus`・`existingListingReason`、公開してほしい理由 `proposeReason`（任意） |
| 詳細 | 提出者、再生リストの概要（サムネイル・タイトル・チャンネル・動画数・ゲーム）と「YouTubeで開く」、動画一覧（YouTube から都度取得・保存しない。`GET /api/admin/workflows/[id]/videos`）、提案時点の掲載状態と公開してほしい理由 |
| ゲームタイトル | 提案のゲームのまま承認するか、承認前に選び直せる（提案の内容は書き換えず、承認時に `editHistory` へ `{ editedAt, operatorId, field: "gameId", from, to }` を足し、`proposalData.approvedGameId`・`approvedGameName` に登録に使った値を残す）。ゲームが分からない提案（`noGame`）はゲームを決めずに承認できる（新しい再生リストはゲーム未設定、すでにある再生リストは今のゲームのまま） |
| 新しいゲームの名前付きの提案 | `proposalData.gameId` が null で `newGameTitle` がある提案は、「① ゲームタイトルを決める → ② 承認・却下」の2段で見せる。①で「〇〇を新しく登録する」（マスタ管理と同じ登録モーダル。楽天ブックスの商品があればその商品、無ければタイトル名と提案の機種を入れて開く）か「既存のゲームタイトルから選ぶ」。決まるまで承認ボタンは押せず、横に「承認するには、先に①でゲームタイトルを決めてください」と出す（API も 400 `game_required`）。登録しただけでは承認しない。提案された名前と完全一致するゲームが登録済みなら自動で選び、その旨を出す（二重登録させない）。却下はいつでも押せる |
| 承認 | 新しい再生リストは、管理者の直接登録（`/api/playlists/register`）と同じ処理で登録する（YouTube・Firestore はサーバー側で取り直す）。チャンネルが未登録なら説明文（任意）を承認時に書ける。すでに `playlists` にある掲載していない再生リストは掲載（`listed`、`listingSetBy: admin`、掲載の既定のタグも付ける）にし、まだ取っていなければ動画一覧を取る。どちらも `playlists.proposedBy` に提案者を残す |
| 承認できないとき | 掲載チャンネルではなくなった（409 `channel_not_listed`）、運営が手で外した再生リスト（`listingSetBy: admin` で `listed` 以外、`hidden_by_admin`）、YouTube で非公開・見つからない（`not_public`・`playlist_not_found`）、登録済み（`already_registered`）、YouTube の取得上限（`quota_exceeded`）。エラーを出し審査中のまま残す |
| 部分失敗 | 登録は済んだがワークフローの更新に失敗した場合は、もう一度の承認で「この提案者の提案として登録済み」（`playlists.proposedBy` が提出者と一致）を確かめて承認済みにする |
| 却下 | 定型の見送り理由から1つを必須で選ぶ（`proposalData.rejectReasonCode` に保存。文言は提案者への通知と提案履歴にそのまま出す）。自由記述は内部メモ。却下された再生リストは再提案できる |

見送り理由（定型。2026-10-25 ユーザー決定）:

1. すでに登録済み、または同じ提案が審査中
2. ゲーム実況の再生リストではない
3. 1つのゲームの実況にまとまっていない（複数のゲームが混ざっている）
4. 再生リストが非公開・削除済み、または動画が少なすぎる
5. その他（掲載の基準に合わない）

### 4.3 ゲームタイトル登録提案（`game_title_register`）

ゲーム未設定（`gameId` が null）の再生リストに付けたいゲームを、一般ユーザーが提案する（既存のゲームから選べない場合の入口。再生リスト詳細仕様書 v1.16）。

| 項目 | 仕様 |
|---|---|
| 提案 | ゲームタイトル名（と任意の備考）を送る。同名（タイトル・別名の正規化一致）のゲームがあれば提案できず一覧から選ぶ。同じ再生リストに審査中の提案があれば不可。1人あたり直近24時間に5件まで |
| 記録 | `proposalData`: `playlistId`・`playlistTitle`・`gameTitle`・`note` |
| 詳細 | 対象の再生リストへのリンク・提案のタイトル名・備考 |
| 承認 | 「ゲームタイトルを登録して承認」（登録モーダル、タイトル名入り）か「既存のゲームに付けて承認」（表記ゆれ・別名扱い）を選ぶ。登録・選んだゲームの ID を `createdGameId` で送り、`proposalData.createdGameId` に残す。承認すると対象の再生リストにそのゲームが付く（履歴 `playlist_game_changes`） |
| 承認できないとき | 提案のあとにユーザーの登録や自動照合で別のゲームが付いた場合は承認せず、「すでに別のゲームが付いているため承認できません。却下してください」と出す（409 `playlist_game_already_set`）。同じゲームが付いていれば成功として承認する。ゲームが無い（404 `game_not_found`）。付けるときに再生リストが無い・付けられないゲームだった場合は、その理由（`playlist_not_found`・`game_not_found`・`rejected_game`。`lib/playlist-game-linking.ts` の `linkPlaylistToGame` の結果）を 409 で返す |
| 却下 | 自由記述の理由が必須（内部メモ） |

> **旧形式**: 2026-10-25 までは、再生リストの提案とは別にゲームタイトルだけを提案できた（`proposalData.playlistUrl` 付き、`playlistId` なし）。今は作られない。作成済みの記録は同じ画面で「ゲームタイトルを登録して承認」でき、承認後は「この再生リストも登録する」（同じ提案の再生リストURLとゲームを入れた `/propose?gameId=…&url=…`）を出す。旧形式は通知しない。本番に審査中の旧形式が残っていないことを確かめたら、この分岐は外してよい。

### 4.4 チャンネル申請（`channel_application`）

入口と受け付けのルールは「ページ 提案する 仕様書」§6（旧「ページ チャンネルを申請する 仕様書」）。

| 項目 | 内容 |
|---|---|
| 起票 | ログイン済みの一般ユーザー（管理者は申請せず、掲載チャンネル画面から直接登録する） |
| 記録 | `proposalData`: 入力した `channelUrl`、`youtubeChannelId`・`channelTitle`・`channelIconUrl`・`subscriberCount`、申請の理由 `reason`（任意）。申請者の区分（本人・事務所／視聴者の推薦）は 2026-11-16 以降は聞かず記録もしない |
| 本人確認 | しない。掲載の判断は申請者ではなくチャンネルそのもの（本人・公式のチャンネルか）を見て行うため |
| 詳細 | チャンネルのアイコン・名前・登録者数・YouTube へのリンク、チャンネルの再生リスト（最大20件、YouTube から都度取得・保存しない。`GET /api/admin/workflows/[id]/channel-playlists`）、申請の理由、掲載チャンネルとしての今の状態（未登録・掲載しない・掲載中・掲載停止） |
| 承認 | 掲載チャンネル（`exploration_channels`）に `status: active`・`publishMode: confirm`・`authorizedVia: channel_application`（2026-11-15 までは `creator_application`／`viewer_recommendation`）で加え、`proposalData.explorationChannelId` に残す。既に `active` なら承認済みにだけする。同じ YouTube チャンネルのドキュメント（未特定・確認待ち・`excluded`）があればそれを `active` にし、無ければ新しく作る。承認の応答のあとに再生リストを1回取り込む（掲載状態は確認待ちになる。取り込みに失敗しても承認は取り消さない。次の巡回で拾う） |
| 承認できないとき | `opted_out`（掲載停止）のチャンネル（409 `channel_opted_out`。掲載チャンネル画面で再開してから承認する） |
| 却下 | 定型の見送り理由（下）から1つを必須で選ぶ。自由記述は内部メモ |
| 重複 | 同じチャンネルの審査中の申請があるときは、2件目以降を受け付けない（2026-11-04 ユーザー決定）。推薦の数は数えない |
| 上限 | 1人1日（日本時間）あたり5件 |
| 申請を受けないチャンネル | 既に登録済み（`active`）・掲載停止（`opted_out`）のチャンネル |

見送り理由（定型）:

1. 実況者本人・公式のチャンネルではない（切り抜き・転載・まとめなど）
2. ゲーム実況の再生リストがほとんどない
3. すでに掲載中、または同じチャンネルの申請が審査中
4. チャンネルが見つからない・非公開
5. その他（掲載の基準に合わない）

### 4.5 詳細ページからの変更の提案（`game_title_edit`・`channel_report`・`playlist_report`）

ゲーム・チャンネル・再生リストの各詳細ページの「情報の更新を提案する」から届く報告。画面と受け付けのルールは「ページ 詳細ページからの変更提案 仕様書」で定める。

| 項目 | 内容 |
|---|---|
| 種別 | ゲーム `game_title_edit`、チャンネル `channel_report`、再生リスト `playlist_report` |
| 記録 | 1人の提案を1件にする。`reportData.targetKey`（`"{種別}:{ID}"`）で同じ対象の提案を引く |
| 一覧 | 「通報」セクションに、対象ごとに1行で並べる（審査中は `targetKey`、処理済みは `reportData.decisionId` でまとめる）。行に人数・いちばん多い理由・対象名を出す。リンク先はまとめのうち最も古い提案 |
| 詳細 | 対象（詳細ページへのリンク。再生リストは今のゲームと掲載状態）、報告の一覧（報告した人・理由・補足・正しいゲーム・二重登録の相手・日時）、承認したときの処理の選択 |
| 承認の処理 | 再生リスト: 「ゲームではない」（`non_game`）／「対象外」（`excluded`）にする（`listingSetBy: admin`、`listingReason: report`）／ゲームを付け替える（外したゲームは `rejectedGameIds` に足す。履歴 `playlist_game_changes`）／処理なし。チャンネル: 掲載から外す（掲載チャンネル画面の「掲載から外す」と同じ。すでに外れている・止めているなら何もしない）／処理なし。ゲーム: 処理なし（運営がゲーム詳細の編集で直してから承認） |
| 既定の処理 | いちばん多い理由から決める（ゲーム実況ではない→ゲームではない、複数のゲーム→対象外、ゲームが違う→付け替え（いちばん多く選ばれたゲーム）、チャンネルの報告→掲載から外す、その他→処理なし）。運営は選び直せる |
| まとめて処理 | 承認・却下すると、押した時点までに届いた同じ対象の審査中の提案をすべて同じ結果にし、`reportData.decisionId`（操作した提案のID）と `step2History`（`approveAction`・付け替えたゲームを含む）を書く。処理中に届いた提案は審査中に残す |
| 見送り理由（定型・必須） | 1. 確認しましたが、今の内容で合っていました 2. すでに直っています 3. 内容を確かめられませんでした 4. その他（掲載の基準に合わせて判断しました）。自由記述は内部メモ |
| 同時操作 | 操作した提案に `approvingAt` を立ててから処理する（§3.3）。状態の確定と、報告した全員への通知は1つのトランザクションで書く |

### 5.1 一覧（`/admin/workflows`）

```
┌─────────────────────────────────────────────┐
│ 審査ワークフロー                              │
│                                             │
│ 通報 （XX件）                                 │
│ [すべて] [未処理] [承認] [却下]               │
│ ┌ [審査中]                2026/11/17 10:00 ┐ │
│ │ スパム・宣伝 — 「〇〇」のレビュー          │ │
│ └──────────────────────────────────────────┘ │
│ ┌ [審査中]                                  ┐ │
│ │ 変更の提案（再生リスト）3人 — … — 「〇〇」 │ │
│ └──────────────────────────────────────────┘ │
│ ページネーション（20件ずつ）                   │
│                                             │
│ 提案 （XX件）                                 │
│ [すべて] [未処理] [承認] [却下]               │

│ └──────────────────────────────────────────┘ │
│ ページネーション（20件ずつ）                   │
└─────────────────────────────────────────────┘
```

- 「通報」（レビューコメント通報・変更の提案）を上、「提案」（再生リスト登録提案・ゲームタイトル登録提案・チャンネル申請）を下に置く。各セクションがタブとページングを別々に持つ。
- タブは「すべて／未処理／承認／却下」。タブに件数を出す。各行は状態・提出日時・概要（種別と対象の名前）で、押すと詳細へ移る。新しい順。
- 読み込みは `workflows` を `type` の等価条件（変更の提案・提案は `in`）だけで行い、タブ・並び順・ページングは画面側で行う（複合インデックスを増やさない）。
- 何も無いときは「通報はありません」「提案はありません」と案内を出す。

### 5.2 詳細（`/admin/workflows/[workflowId]`）

- 上から「一覧へ戻る」、見出し、種別ごとの詳細（§4）。どの種別も共通で、見出し部分（審査種別・提出日時・提出者（通報は出さない）・状態）、申請内容、承認・却下の結果の記録（最新の `step2History` のコメント）、運営メモ（§3.5）、審査中なら「却下する」「承認する」ボタンを出す。
- ワークフローを購読し、承認・却下の結果をそのまま反映する。扱わない種別・存在しない ID は 404。
- 承認・却下の実行中はボタンを押せない。

### 5.3 未処理の件数

未処理（審査中）の件数を、次の場所に出す。数え方はどこでも同じで、一覧の行の数と揃える（通報＝レビューコメント通報＋変更の提案の対象の数、提案＝3種別の件数）。

| 場所 | 出すもの |
|---|---|
| 管理画面のダッシュボード（`/admin`）の審査ワークフローのカード | 通報・提案の件数を並べる（v14.0 から通報に変更の提案も含める） |
| 管理画面の「審査ワークフロー」タブ、サービス側のユーザーメニュー（アイコンと「管理画面」項目）、マイページ | 通報＋提案の合計のバッジ（99件を超えたら「99+」） |

- ページを移るたびに取り直す（リアルタイムでは更新しない）。管理者以外には出さない。
- 件数は `status == 'reviewing_lv1'` の記録だけを読んで数える（`reviewing_lv2` は作られないため。§3.1）。

## 6. 実装の構成

v14.0（2026-11-17、リファクタリング③）で、承認・却下の処理を種別ごとのファイルに分け、画面の読み込みを lib にまとめた。種別を足す・変えるときは、ここに挙げたファイルだけを見ればよいようにする。

### 6.1 API

| API | 中身 |
|---|---|
| `PATCH /api/admin/workflows/[workflowId]` | `action: update_memo`（運営メモ）／`approve`／`reject`。ルートは管理者の確認・ワークフローの読み込み・運営メモの保存・審査中かの確認だけを行い、承認・却下は種別ごとの処理へ渡す。応答は `{ ok: true, ...種別ごとの項目 }`（チャンネル申請は `imported`、変更の提案は `count`）か `{ error, message? }`。共通のエラーは、ワークフローが無い 404 `not_found`、扱えない種別 400 `unsupported_type`、`action` が不正 400 `invalid_action`、運営メモが文字列でない 400 `invalid_request`、審査中でない 409 `already_processed`、記録の中身が足りない 400 `invalid_workflow`（チャンネル申請・変更の提案）。種別ごとのエラーは §4 |
| `GET /api/admin/workflows/[workflowId]/videos` | 再生リスト登録提案の動画一覧（§4.2） |
| `GET /api/admin/workflows/[workflowId]/channel-playlists` | チャンネル申請のチャンネルの再生リストと掲載チャンネルとしての状態（§4.4） |

### 6.2 サーバー側（`lib/`）

| ファイル | 役割 |
|---|---|
| `workflow-decisions.ts` | 種別 → 承認・却下の処理の表（`workflowDecisionHandler`）。**種別を足すときはここに1行足す** |
| `workflow-server.ts` | 種別をまたぐ処理: 承認処理中の印を取る・外す（`claimApproving`・`releaseApproving`）、状態の確定と通知を1回だけ書く（`commitDecision`）、処理の型（`WorkflowDecisionHandler`） |
| `workflow-shared.ts` | 画面・サーバー共用（DB を使わない）: 状態、印の有効期間（2分）、運営メモ・コメントの整え方、`step2History` の1件、通知の形、未処理の数え方。単体テスト `tests/unit/workflow.test.ts` |
| `review-report-server.ts` | §4.1 レビューコメント通報 |
| `playlist-proposal-server.ts` | §4.2 再生リスト登録提案（登録は `playlist-registration.ts`、すでにある再生リストの掲載は `propose-server.ts`） |
| `game-proposal-server.ts` | §4.3 ゲームタイトル登録提案（ゲームを付けるのは `playlist-game-linking.ts`） |
| `channel-application-server.ts` | §4.4 チャンネル申請（受け付けと承認。取り込みは `channel-sweep-run.ts`） |
| `change-proposal-server.ts` | §4.5 変更の提案（受け付けと承認） |
| `proposal-shared.ts`・`channel-application-shared.ts`・`change-proposal-shared.ts`・`report-reasons.ts` | 種別ごとの定数（種別名・見送り理由・通知の文面・まとめ方）。画面と共用 |

### 6.3 画面側

| ファイル | 役割 |
|---|---|
| `app/admin/workflows/page.tsx` | 一覧（§5.1） |
| `app/admin/workflows/[workflowId]/page.tsx` | 詳細の振り分け（種別 → 部品の表） |
| `components/admin/workflows/*Detail.tsx` | 種別ごとの詳細（§4.1〜§4.5） |
| `components/admin/workflows/shared.tsx` | 共通の部品（見出し・結果の記録・運営メモ・ボタン・確認ダイアログ） |
| `lib/workflow-admin.ts` | 審査画面の読み込み（一覧の行、詳細の購読、未処理の件数）と審査 API の呼び出し（`callWorkflowApi`） |
| `lib/admin-api.ts` | 管理 API を ID トークン付きで呼ぶ共通の関数（`requestAdminApi`・`callAdminApi`・`adminFetch`。エラーは `AdminApiError` の `code`） |
| `lib/admin-reads.ts` | 管理画面で共通の読み込み（ゲームの一覧・表示名など） |

- 管理画面・審査画面の部品（`app/admin/**`・`components/admin/**`）からは Firestore を直接読まない。読み込みは `lib/*-admin.ts`・`lib/admin-reads.ts`、書き込みは管理 API（ESLint の `no-restricted-imports` で止める）。

### 6.4 種別を足すときの手順

1. `workflows.type` の名前を決め、種別ごとの定数のファイル（`*-shared.ts`）に置く。
2. 受け付けの API を作り、`lib/playlist-registration.ts` の `newWorkflowRecord` で `reviewing_lv1` のワークフローを作る。
3. `lib/<種別>-server.ts` に `WorkflowDecisionHandler` を作る（`claimApproving`・`commitDecision` を使う）。`lib/workflow-decisions.ts` の表に1行足す。
4. 詳細の部品（`components/admin/workflows/`）を作り、`app/admin/workflows/[workflowId]/page.tsx` の表に足す。一覧のどちらのセクションに出すか（`lib/workflow-admin.ts`）と、未処理の数え方（`countPendingWorkflows`）に足す。
5. 本書の §4 に節を足し、純粋な部分（通知の文面など）に単体テスト、画面に E2E を足す。
